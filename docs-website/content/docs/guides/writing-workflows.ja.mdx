[ワークフロー](/ja/docs/concepts/how-it-works#workflow)ファイルは、プライマリリポジトリの `.codedag/dags/` ディレクトリに置く YAML または JSON のファイルで、実行するタスクとタスク間の依存関係を記述します。必須なのは、各タスクの `id`、`title`、`prompt` だけです。タスクをどのエージェントが実行するか、実行中に許可を待つかどうか、完了後にレビューを待つかどうかは、それぞれ省略可能なフィールドで指定し、書かなければデフォルト値が使われます。

## 手で書きたくない場合

CodeDAG Guide プラグインを入れた Claude Code や Codex にやりたいことを伝えれば、ワークフローファイルの作成、検証、投入、進捗の追跡までを任せられます。方法は[エージェントにオーケストレーションを任せる](/ja/docs/get-started/let-your-agent-orchestrate)を参照してください。エージェントが書いたファイルは手で書いたものと変わらず、同じく `.codedag/dags/` に置かれます。このページの以降の各セクションは、そうしたファイルを読んで確認するときにも役立ちます。

## ファイルの置き場所

ワークフローファイルは、プライマリリポジトリ（`.codedag/` があるリポジトリ）の `.codedag/dags/` ディレクトリに置きます。CodeDAG がワークフローを読み込むのは、このディレクトリからだけです。ファイル名から拡張子を除いたものがワークフローの名前になり、コマンドではこの名前で指定します。たとえば `.codedag/dags/testing-docs.yaml` は、`cdg dag validate testing-docs{:sh}` で検証できます。この名前はタスクブランチ名やログファイル名にも使われるため、短い英小文字の名前にしておくと扱いやすくなります。

ファイル形式は YAML（`.yaml`、`.yml`）と JSON（`.json`）のどちらでもかまいません。使えるフィールドはまったく同じです。複数行のプロンプトを自然に書け、コメントも付けられるので、YAML をおすすめします。`cdg init` が `.codedag/dags/` に生成する `untitled_dag.yaml` は、コメント付きの空のテンプレートです。コピーして名前を変えれば、そこから書き始められます。

`.codedag/` は、プロジェクトリポジトリから独立した[サイドカーリポジトリ](/ja/docs/concepts/how-it-works#sidecar-repo)です。そのため、新しく作ったワークフローファイルは、プロジェクトリポジトリの `git status` には表示されません。ワークフローファイルの変更履歴を残したい場合は、[ワークフローと共有設定を別に保存する](/ja/docs/reference/branches-and-files#save-config)を参照してください。

## 最小構成 [#minimal-structure]

ワークフローファイルには、少なくとも `tasks` のリストが必要です。リストにはタスクを 1 つ以上書き、各タスクには `id`、`title`、`prompt` を必ず書きます。タスクの前後関係は `dependencies` で表します。次のワークフローには、タスクが 2 つあります。タスク 1 はプロジェクトのテストコマンドをまとめてファイルに書き、タスク 2 はそのファイルを読んで、README にテストの説明を追加します。

```yaml title=".codedag/dags/testing-docs.yaml"
tasks:                                # タスクのリスト。タスクが 1 つ以上必要
  - id: 1                             # タスク番号。ワークフロー内で一意の正の整数
    title: テストコマンドをまとめる   # 人が読むための短いタイトル。ステータスボードに表示される
    prompt: |                         # タスクエージェントへの指示。| は、以降が複数行のテキストであることを表す
      リポジトリにあるビルドとテストの設定（package.json、Makefile、CI の設定など）を読み、
      すべてのテストをローカルで実行するコマンドと、そのために必要な準備の手順を調べて、
      docs/notes/testing.md に書いてください。
      書くのはこのファイルだけです（すでにある場合はそのまま上書きします）。ほかのファイルは変更しないでください。

  - id: 2
    title: READMEにテストの説明を追加
    dependencies: [1]                 # タスク 1 が完了して承認されてから開始する
    prompt: |
      docs/notes/testing.md を読み、README.md に「テストの実行」という節を追加して、
      ローカルでテストを実行する方法を 3〜5 ステップで説明してください。変更するのは README.md だけにしてください。
```

タスク 2 のプロンプトには、読むファイルのパスを明記しています。どのタスクも新しいエージェントセッションで、上流タスクの会話は見えず、上流がリポジトリに残したファイルしか読めないからです。タスクの分け方とプロンプトの書き方は、[タスクの分割とプロンプトの書き方](/ja/docs/guides/designing-tasks-and-prompts)を参照してください。

プロンプトが 1 行だけであれば、コロンの後ろにそのまま書けます。ただし、内容に半角コロンとスペースの組み合わせ（`Goal: ...` など）が含まれていると、YAML がそれをキーと値のペアと解釈して、構文エラーになります。その場合も、`|` を使った複数行の書き方にしてください。

このファイルはすでに検証に通りますが、どのエージェントが実行するかも、権限モードも指定していません。このまま投入すると、2 つのタスクはどちらもプロジェクトのデフォルトのエージェントが実行し、そのエージェント自身の権限設定がそのまま使われます。その設定がファイルの変更やコマンドの実行に許可を求めるものであれば、タスクは止まって人の応答を待ちます。実際に投入するときは、通常、各タスクに `agent` と `mode` も書きます。書き方は[よく使うフィールド](#common-fields)を参照してください。

## よく使うフィールド [#common-fields]

実行の制御でよくある要望には、それぞれ対応するフィールドがあります。「タスク」と記したフィールドは `tasks` の各項目の中に書き、そのタスクだけに影響します。「ワークフロー」と記したフィールドは、ファイルのトップレベルに `tasks` と並べて書き、ワークフロー全体に適用されます。

| やりたいこと | フィールド | 省略した場合 | 説明 |
|---|---|---|---|
| タスクを実行するエージェントを指定する | `agent`（タスク） | プロジェクトのデフォルトのエージェント。`cdg init` のときに決まります | `claude` は Claude Code、`codex` は Codex を指します。両者に作業を分担させる書き方は、[Claude Code と Codex を組み合わせる](/ja/docs/guides/mixing-agents)を参照してください。 |
| モデルや推論エフォートを指定する | `model`、`effort`（タスク） | エージェント側で設定されているデフォルト値 | エージェントにそのまま渡されます。指定できる値は、そのエージェントのドキュメントに従います。 |
| タスクが実行中に止まって許可を待つかどうかを決める | `mode`（タスク） | エージェント自身の権限設定 | 書き方はエージェントによって異なります。無人実行では通常フルアクセスを使い、Claude Code では `bypassPermissions`、Codex では `yolo` と書きます。アクセスレベルごとのトレードオフは、[無人実行か有人実行かを決める](/ja/docs/guides/agents-and-permission-modes#unattended-or-attended)を参照してください。 |
| 特定のタスクを完了後に止め、レビューを待たせる | `autoAccepted: none`（タスク） | 自動承認 | このタスクの結果を承認するまで、下流のタスクは開始されません。レビューの方法は[タスクとワークフローをレビューする](/ja/docs/guides/review-tasks)を参照してください。 |
| すべてのタスクを完了後に止め、レビューを待たせる | `taskAutoAccepted: none`（ワークフロー） | 自動承認 | すべてのタスクに `autoAccepted: none` を書いたのと同じです。タスク自身に `autoAccepted` が書かれている場合は、タスクの値が優先されます。 |
| ワークフロー全体を終了前に止め、結論を出すまで待たせる | `dagAutoAccepted: none`（ワークフロー） | 自動承認 | すべてのタスクが完了した後、ワークフロー全体の結果について、承認、キャンセル、見送りのいずれかの結論を自分で出します。 |
| 同時に実行するタスクの数を制限する | `maxConcurrency`（ワークフロー） | プロジェクト設定の値。`cdg init` は、レプリカの数に 1 を足した値を書き込みます。プロジェクト設定にもなければ 1 | 分離ブランチモードでは、実際の同時実行数が、利用できるワークスペースの数を超えることもありません。[同時に実行されるタスクの数は何で決まるか](/ja/docs/guides/parallel-workspaces#concurrency)を参照してください。 |
| ブランチの作成もコミットもせず、すべてのタスクを同じワークスペースでそのまま実行する | `executionMode: shared-workspace`（ワークフロー） | `isolated-branches`（分離ブランチモード）。各タスクは専用のブランチで実行されます | 共有ワークスペースモードです。デフォルトではプライマリリポジトリで実行されます。ドキュメントの作成や調査のように、コンパイルもテストの実行もしないタスクに向いています。2 つのモードの違いは、[実行モード](/ja/docs/concepts/workspaces-and-branches#execution-modes)を参照してください。 |

「省略した場合」の列は、ほかに何も設定していないときの結果です。このうちいくつかの項目は、プロジェクト設定や `cdg dag submit` のオプションでも設定できます。同じ項目を複数の場所で設定した場合は、投入コマンドのオプションがファイルのフィールドより優先され、タスクのフィールドがワークフローのフィールドより優先され、ファイルのフィールドがプロジェクト設定より優先されます。優先順位の全体は、[デフォルト値と優先順位](/ja/docs/reference/workflow-file#precedence)を参照してください。

次の例は、最小構成の例にフィールドを書き足し、実際に投入する形にしたものです。使用するエージェントに合わせて、どちらかのバージョンを選んでください。

```yaml title=".codedag/dags/testing-docs.yaml"
tasks:
  - id: 1
    title: テストコマンドをまとめる
    agent: claude             # Claude Code が実行する
    mode: bypassPermissions   # フルアクセス。実行中に許可待ちで止まらない
    model: sonnet             # 情報をまとめる作業なので、速いモデルを使う
    autoAccepted: none        # 完了したら止まり、結果の確認を待ってから先へ進む
    prompt: |
      リポジトリにあるビルドとテストの設定（package.json、Makefile、CI の設定など）を読み、
      すべてのテストをローカルで実行するコマンドと、そのために必要な準備の手順を調べて、
      docs/notes/testing.md に書いてください。
      書くのはこのファイルだけです（すでにある場合はそのまま上書きします）。ほかのファイルは変更しないでください。

  - id: 2
    title: READMEにテストの説明を追加
    dependencies: [1]
    agent: claude
    mode: bypassPermissions
    model: opus               # 読者に向けた文章なので、より高性能なモデルを使う
    prompt: |
      docs/notes/testing.md を読み、README.md に「テストの実行」という節を追加して、
      ローカルでテストを実行する方法を 3〜5 ステップで説明してください。変更するのは README.md だけにしてください。
```

    dependencies: [1]

タスク 1 が完了すると、ワークフローは止まってレビューを待ちます。タスク 1 がまとめた内容を確認してから `cdg task review accept 1 -w testing-docs{:sh}` を実行して結果を承認すると、タスク 2 が開始されます。

## 検証する [#validate]

`cdg dag validate` は、ワークフローファイルの形式、フィールドの値、依存関係をローカルでチェックします。ログインは不要で、クレジットも消費しないため、書いている途中で何度でも実行できます。ワークフロー名を複数並べれば、まとめて検証できます。

```bash title="Terminal"
cdg dag validate testing-docs
```

結果は、成功、警告付きの成功、失敗の 3 種類です。失敗した場合は、エラーが 1 件ずつ出力されます。たとえば、タスク 2 が存在しないタスク 3 に依存している場合は、次のようになります。

```bash title="Terminal"
✗ Validation failed: .codedag/dags/testing-docs.yaml
  [dag] Task 2: depends on non-existent task 3
```

検証で読み込まれるのは、このファイルだけではありません。2 つのプロジェクト設定ファイルも一緒に読み込まれ、設定項目の値が不正な場合は、検証はその時点で失敗し、どのファイルのどの項目かが示されます。フィールドの値のうち、`mode` は、タスクが実際に使うエージェントの書き方に合っているかどうかがチェックされます。一方、`model` や `effort` のようにエージェントにそのまま渡される値は、チェックの対象外です。各フィールドで何がチェックされるかは、[ワークフローファイルリファレンス](/ja/docs/reference/workflow-file)を参照してください。

警告があっても検証は失敗しませんが、1 件ずつ確認しておくことをおすすめします。最もよくあるのは `unsupported-field` です。CodeDAG は、ワークフローファイルにある未知のフィールドを無視します。そのため、フィールド名のつづりを間違えてもエラーにはならず、そのフィールドが効かないだけです。フィールド名はすべて camelCase で書きます。`auto_accepted` のように snake_case で書いた場合も同じく無視され、あわせて `naming` の警告が、`autoAccepted` に直すよう促します。

投入時には、`cdg dag submit` がもう一度検証を実行し、エラーがあれば投入されません。検証や投入に失敗したときの調べ方は、[投入が拒否された](/ja/docs/troubleshooting/troubleshooting#submit-rejected)を参照してください。
