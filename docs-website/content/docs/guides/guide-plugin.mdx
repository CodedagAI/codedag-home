## What the plugin is [#what-it-is]

The CodeDAG Guide plugin gives Claude Code and Codex a skill for using CodeDAG, named `codedag-guide`. Once it's installed, you describe your goal in plain language, and the agent can split the work into tasks and write the workflow file on its own, then use `cdg` to validate and submit it, track progress, and handle reviews. In short, it does the orchestrating for you. For how to use it, see [Let Your Agent Orchestrate](/docs/get-started/let-your-agent-orchestrate).

The plugin is published in the GitHub repository `CodedagAI/codedag-plugin-marketplace`. Claude Code and Codex both add this repository as a marketplace named `codedag`, and the plugin's identifier is `codedag@codedag` in both agents. Whenever the plugin is installed or updated, Claude Code and Codex fetch it from this repository themselves. Day to day, you manage it with `cdg plugin{:sh}`, which calls each agent's own plugin commands for you, so a single command takes care of both agents. The plugin and the CLI are released separately and updated independently.

## Install the plugin [#install]

You can install the plugin as part of initializing CodeDAG in a project:

```bash title="Terminal"
cdg init
```

During initialization, the command asks once for each agent installed on this machine whether to install the plugin. Agents that already have the plugin aren't asked. Here's the question for Claude Code (Codex's options are largely the same):

```bash title="Terminal"
? Install the CodeDAG plugin for Claude Code?
  Choose which Claude Code settings enable it. …
❯ 1. User-level (Claude Code user settings — applies to all your projects)
  2. Project-level (shared with your team through .claude/settings.json)
  3. Local (.claude/settings.local.json — ignored by Git; linked worktrees share the main worktree's file)
  4. Skip (install later with `cdg plugin install --claude --scope user|project|local` or Claude Code native plugin install)
```

The first three options are the three installation scopes, and we recommend simply choosing `1. User-level`. Choose Skip to leave the plugin uninstalled for now.

If you skipped the plugin during initialization, or installed the other agent only later, install it with this command:

```bash title="Terminal"
cdg plugin install
```

It installs the plugin at the default user scope for each agent installed on this machine, and skips any agent that already has it.

The plugin takes effect only in new sessions. A Claude Code or Codex session that was already open before you installed the plugin can't see it. Exit that session and resume it with `claude --resume{:sh}` or `codex resume{:sh}`, and you can use the plugin in the same conversation.

### Choose an installation scope [#scopes]

The plugin is installed at the user scope by default, which takes effect in every repository on this computer: install once, and sessions in all of them can use it. There are also two other scopes: the project scope shares the plugin with your team along with the repository, and the local scope takes effect only on this computer. In most cases, just use the default user scope.

To install at the project or local scope, specify it with `--scope` when you install. To install for just one of the agents, add `--claude` or `--codex`:

```bash title="Terminal"
# Install for Claude Code only, at the project scope
cdg plugin install --claude --scope project
```

For which files each of these two scopes has you commit or ignore, and how each one behaves across multiple worktrees, see [Installation scopes](/docs/reference/cli/plugin#scopes) in the plugin reference.

## Check the installation status [#status]

To confirm whether the plugin is installed properly and which scope it's installed at, run `cdg plugin status{:sh}` in the repository where you use the agent. It prints a set of fields for each agent, including whether the plugin is installed (`Plugin installed`), its installation scope (`Scope`), whether it's enabled (`Enabled`), and whether the installation is intact and current with the latest version the agent knows about (`Sync`). The last line, `Action`, gives the next step. When it shows `No action needed`, there's nothing to do. Otherwise, run the command it gives. To look at just one agent, add `--claude` or `--codex`.

The directory you run the command in affects the result. A user-scope installation is visible from any directory, while project-scope and local-scope installations are visible only when you run the command in the corresponding repository. So seeing `Plugin installed: false` in some other directory doesn't mean the plugin isn't installed in this repository.

`cdg plugin status{:sh}` doesn't go online. It compares the installed plugin with the copy of the plugin repository that the agent keeps locally. If a new version has been released on GitHub but the agent hasn't refreshed its local copy yet, it still shows `Sync: up to date`. To make sure you're on the latest version, just run [`cdg plugin update`](#update).

## Update the plugin [#update]

Run `cdg plugin update{:sh}`. CodeDAG first has the agent fetch the latest contents of the plugin repository from GitHub, then updates the installed plugin to the latest version. By default, it covers every agent installed on this machine. Add `--claude` or `--codex` to update just one. The update stays within the plugin's existing scope and keeps your choice of enabled or disabled in the agent. Like a newly installed plugin, an updated one takes effect only in new sessions.

```bash title="Terminal"
cdg plugin update
```

Codex updates the whole `codedag` marketplace as a unit, so any other plugins you've installed from that marketplace are updated along with it. The command lists each plugin it updated.

Both agents also update plugins on their own, but in different ways. Every time Codex starts, it refreshes marketplaces added from Git repositories in the background and reinstalls any plugins that changed, so you usually don't need to update the plugin in Codex by hand. Claude Code doesn't auto-update this marketplace by default. You can run `cdg plugin update{:sh}` every so often, or run `/plugin` in a Claude Code session, select `codedag` on the Marketplaces tab, and choose Enable auto-update. From then on, Claude Code updates the plugin automatically whenever a session starts. Right after you upgrade the CLI is also a good time to update. For the reason, see [Do I need to update the plugin after upgrading the CLI?](#after-cli-upgrade).

### Customize orchestration to the way you work [#customize]

If you want the agent to orchestrate the way you like, such as which access level to use by default or which kinds of tasks to follow with a manual review, put those requirements in your project's CLAUDE.md (Claude Code) or AGENTS.md (Codex) rather than editing the plugin's skill files directly. Requirements written in CLAUDE.md or AGENTS.md aren't affected by plugin updates, and they can be shared with your team along with the repository. If you edit the skill files instead, every update makes you choose between keeping your edits and switching to the new version, and any edits you want to keep have to be moved out by hand.

If you've already edited the skill files directly, keep two things in mind when you update:

- **Updates keep your edits by default:** When you run `cdg plugin update{:sh}` in a terminal, the command first asks whether to back up those files and switch back to the released contents, and the default is not to. When an agent or a script runs it, the command doesn't ask. It keeps your edits, so this plugin isn't updated this time, and for Codex, neither is the rest of the `codedag` marketplace.
- **When you're sure you no longer need those edits:** First move any requirements you still want to keep into CLAUDE.md or AGENTS.md, then run the update with `--reset-local-changes`:

  ```bash title="Terminal"
  cdg plugin update --reset-local-changes
  ```

  The command then skips the question, backs up the edited plugin, and replaces it with the latest release from the plugin repository. Even if there's no new version of the plugin, the edited files go back to their released state right away. For where the backup goes, see [--reset-local-changes](/docs/reference/cli/plugin#reset-local-changes).

## Change the installation scope or uninstall [#change-scope]

To change the scope, first uninstall the plugin with `cdg plugin uninstall{:sh}`, then install it with the new `--scope`, and finally open a new session. A plugin at the project or local scope has to be uninstalled from inside the repository where it's installed, and to handle only one agent, add `--claude` or `--codex`. If all you want is to uninstall, the first step is enough. You can't change the scope of an installed plugin directly. If you run `cdg plugin install --scope <scope>{:sh}` on it again, the command only reports the scope the plugin is already installed at and skips it.

The uninstall command has no `--scope` option. It removes every installation that's visible from where you run it, and inside a repository, that includes the user-scope installation. Uninstalling from the project scope changes a version-controlled configuration file, and that change needs to be committed too. For which installations are removed from which directory, how to stop using the plugin just for yourself when your team uses the project scope, and what to do with the file that the local scope leaves behind, see [cdg plugin uninstall](/docs/reference/cli/plugin#uninstall). For complete examples of changing the scope in both directions, see [Change the installation scope](/docs/reference/cli/plugin#change-scope).

## Install with the agent's own commands [#manual-install]

You can also install the plugin without going through `cdg`, using Claude Code's or Codex's own plugin commands. First add the GitHub repository `CodedagAI/codedag-plugin-marketplace` as a marketplace (named `codedag`), then install `codedag@codedag` from it. That's a good fit if you prefer to manage all your plugins from within the agent. Otherwise, a single `cdg plugin install{:sh}` command installs the plugin for both agents.

<Tabs items={['Claude Code', 'Codex']}>
  <Tab value="Claude Code">

```bash title="Terminal"
claude plugin marketplace add CodedagAI/codedag-plugin-marketplace
claude plugin install codedag@codedag
```

The second command installs at the user scope by default. To install at the project or local scope, add `--scope project` or `--scope local`.

  </Tab>
  <Tab value="Codex">

```bash title="Terminal"
codex plugin marketplace add CodedagAI/codedag-plugin-marketplace
codex plugin add codedag@codedag
```

Codex's own commands can install only at the user scope. To install at the project or local scope, use `cdg plugin install --codex --scope project{:sh}` or `--scope local`.

  </Tab>
</Tabs>

As with `cdg plugin install{:sh}`, the plugin takes effect only after you open a new session. A plugin installed this way can still be checked with `cdg plugin status{:sh}` and updated with `cdg plugin update{:sh}`. To update it through the agent's own commands instead, run `claude plugin update codedag@codedag{:sh}` for Claude Code (adding the matching `--scope` if it's installed at the project or local scope), or `codex plugin marketplace upgrade codedag{:sh}` for Codex.

## Common questions

### The plugin is installed, but the agent still doesn't know how to use CodeDAG

The most common cause is that the session was opened before the plugin was installed. The plugin takes effect only in new sessions, so exit the current session and resume it with `claude --resume{:sh}` or `codex resume{:sh}`.

If that doesn't help, run `cdg plugin status{:sh}` in this repository, find the agent you're using, and follow the command or entry point given on its last line, `Action`. To see where the problem lies, look at the fields above `Action`:

- **`Plugin installed: false`:** The plugin for this agent isn't visible from this repository. Possible reasons:
  - The plugin was installed only for the other agent.
  - The plugin was installed at the project or local scope in a different repository.
- **`Sync: broken`:** The installation isn't intact. A common case is that your team committed project-scope configuration, but the plugin isn't installed on your computer yet.
- **`Enabled: false`:** The plugin has been disabled in the agent. For which scope's setting applies when several are present, see [When more than one scope is present](/docs/reference/cli/plugin#multiple-scopes).

### Do I need to update the plugin after upgrading the CLI? [#after-cli-upgrade]

We recommend updating, but you don't have to. The CLI and the plugin are released separately, and upgrading the CLI doesn't update the plugin along with it. A new CLI version keeps the commands and arguments that released plugins use, along with their meanings, so even without a plugin update, the agent still uses the CLI correctly. It just doesn't know about anything the new version adds. After you upgrade the CLI, run `cdg plugin update{:sh}` once so the agent can use those additions.

It also works the other way around: if the plugin is newer than your CLI and requires a later CLI version, `cdg init{:sh}` and `cdg dag submit{:sh}` show a warning. In that case, it's the CLI you need to upgrade. See [Version compatibility](/docs/reference/cli/plugin#compatibility).
