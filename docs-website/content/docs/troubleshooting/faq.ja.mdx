タスクが止まった、投入が拒否された、ログインに失敗した、といった具体的なトラブルの場合は、[トラブルシューティング](/ja/docs/troubleshooting/troubleshooting)で症状から調べるほうが早く解決できます。

## 概念

<Accordions type="single">
<Accordion title="ワークフロー、dag、DAG は同じものですか" id="workflow-and-dag">

同じものです。ドキュメントでは「ワークフロー」と呼び、コマンドでは `cdg dag submit{:sh}` のように `dag` と書きます。コマンドのオプションの `--workflow-file` と `--dag` も、同じ意味です。DAG は有向非巡回グラフ（Directed Acyclic Graph）の略で、タスクと依存関係が形作るグラフを指します。製品名の CodeDAG も、コマンドの `dag` も、ここから来ています。[ワークフロー](/ja/docs/concepts/how-it-works#workflow)を参照してください。

</Accordion>
<Accordion title="タスク同士で会話のコンテキストを共有しないのはなぜですか" id="no-shared-context">

どのタスクも、新しいエージェントセッションで実行されるからです。セッションが長くなるほど、コンテキストには関係のない情報が増え、エージェントの判断が当てにならなくなります。タスクごとにまっさらなコンテキストから始めれば、エージェントは最も信頼できる状態で、範囲のはっきりした作業をやり遂げられます。その代わり、上流での会話は下流に引き継がれず、引き継がれるのは、上流がリポジトリに残したファイルだけです。そのため、上流は結論をファイルに書き、下流のプロンプトでは、そのファイルを読むよう明記する必要があります。理由は[タスクを分割する理由と、分割の目安](/ja/docs/concepts/tasks-and-sessions#why-split)、書き方は[結論を下流に渡す](/ja/docs/guides/designing-tasks-and-prompts#pass-results)を参照してください。

</Accordion>
<Accordion title="オーケストレーションエージェントとは何ですか" id="orchestrating-agent">

オーケストレーションエージェントは、ユーザーに代わって `cdg` を操作する Claude Code または Codex のセッションです。CodeDAG Guide プラグインが入っていて、目標の説明を受けると、ワークフローの作成、検証、投入、進捗の追跡、レビューの進行を担当します。ワークフロー内の各タスクのコードを書くのは、この場合もタスクエージェントです。タスクエージェントは、CodeDAG がタスクごとに個別に起動する新しいセッションで、オーケストレーションエージェントとは別のセッションです。それぞれの役割分担は[誰が何を担当するか](/ja/docs/concepts/how-it-works#roles)、使い方は[エージェントにオーケストレーションを任せる](/ja/docs/get-started/let-your-agent-orchestrate)を参照してください。

</Accordion>
<Accordion title="タスクが done になったのに、終わったことにならないのはなぜですか" id="done-is-not-final">

`done` は、タスクエージェントが作業を終えたと判断したことを示すだけです。結果は、このあとレビューゲートを通る必要があります。承認されて初めて、タスクは `reviewed` になり、そのタスクに依存する下流のタスクが始まります。デフォルトでは自動承認されるため、`done` は通常、一瞬しか表示されません。タスクに `autoAccepted: none` を設定している場合や、分離ブランチモードで実行されたタスクが変更を何も残さなかった場合は、タスクが `done` で止まってレビューを待ち、下流も待ち続けます。ゲートの役割は[レビューゲート](/ja/docs/concepts/review-gates#review-gate)、レビューの操作は[タスクとワークフローをレビューする](/ja/docs/guides/review-tasks)を参照してください。

</Accordion>
</Accordions>

## 実行と並列化

<Accordions type="single">
<Accordion title="worktree を使わずに並列実行できますか" id="parallel-without-worktree">

できます。方法は 2 つあります。

- **clone をレプリカにする。** レプリカは git worktree でも完全な clone でも作れますが、1 つのプロジェクトで使えるのはどちらか一方だけです。[worktree と clone のどちらを選ぶか](/ja/docs/guides/parallel-workspaces#worktree-or-clone)を参照してください。
- **共有ワークスペースモードに切り替える。** `executionMode: shared-workspace` と書くと、すべてのタスクが同じディレクトリで実行され、レプリカは必要ありません。同時に実行されるタスクの数は、ワークフローファイルの `maxConcurrency` で決まります。書かない場合はプロジェクト設定の値が使われ、プライマリリポジトリだけを登録したプロジェクトでは、デフォルトで 1 です。このモードでは、CodeDAG はタスクごとの書き込みを分離しません。そのため、向いているのは、コンパイルもテストの実行もせず、それぞれが別のファイルに書き込むタスクだけです。たとえば、ドキュメントの作成、翻訳、調査です。[実行モード](/ja/docs/concepts/workspaces-and-branches#execution-modes)を参照してください。

</Accordion>
<Accordion title="同じプロジェクトの 2 つのワークフローを同時に実行できますか" id="concurrent-workflows">

できません。同じプロジェクトのワークフローは投入順にキューに並び、一度に実行されるのは先頭の 1 つだけです。先頭のワークフローのレビューが終了してキューを離れると、次のワークフローが始まります。並列に実行されるのは、1 つのワークフローの中だけです。互いに関係のない複数の作業を同時に進めたい場合は、同じワークフローの中の、互いに依存しないタスクとして書きます。プロジェクトが違えばキューも別々で、互いに影響しません。[投入とキュー](/ja/docs/concepts/how-it-works#queue)を参照してください。

</Accordion>
<Accordion title="1 つのワークフローで複数のリポジトリを扱えますか" id="multiple-repositories">

扱えません。1 つのワークフローが対象にするのは、1 つのプロジェクトだけです。プロジェクトとは、1 つの Git リポジトリと、そこに登録したレプリカを合わせたものです。複数のリポジトリにまたがる仕事では、リポジトリごとにワークフローを書いて、それぞれ投入します。リポジトリ間の連携は、自分で段取りします。[プロジェクト](/ja/docs/concepts/how-it-works#project)を参照してください。

</Accordion>
<Accordion title="条件分岐やループは使えますか" id="conditions-and-loops">

使えません。ワークフローのタスクと依存関係は、投入した時点で固定されます。CodeDAG が実行結果に応じてタスクを追加・削除することはなく、前のタスクに自動的に戻って実行し直すこともありません。

処理を「状況に応じて」変えたい場合は、使う可能性のあるタスクをすべてあらかじめ並べておき、判断の条件をプロンプトに明記します。条件が成り立たない場合は、あらかじめ決めたファイルに理由だけを記録させます。この記録は省けません。デフォルトの分離ブランチモードでは、何も変更しなかったタスクは `done` で止まり、手動レビューを待つからです。繰り返し試す必要がある作業は、1 つのタスクの中に入れられます。たとえば「すべてのテストを実行して、すべて通るまで修正する」という作業は、タスクエージェントがセッションの中で繰り返し行います。そのほかの制限は、[CodeDAG の現在の制限](/ja/docs/introduction/when-to-use#limitations)を参照してください。

</Accordion>
<Accordion title="実行が長引くタスクに、タイムアウトを設定できますか" id="task-timeout">

できません。CodeDAG にはタスクのタイムアウト設定がなく、実行時間が長いというだけでタスクを強制停止することはありません。長い間新しい出力がなくても、止まったままになっているとは限りません。タスクエージェントがサブエージェントを起動して、バックグラウンドで作業させている可能性があります。止まったままかどうかを見分ける方法と、実際に止まっていた場合に強制停止し、そのあと元のセッションで続きから再開させる方法は、[タスクに長時間新しい出力がない](/ja/docs/troubleshooting/troubleshooting#no-output)を参照してください。

</Accordion>
<Accordion title="DAG を可視化する画面はありますか" id="visual-interface">

GUI はありません。実行の状況は、すべてターミナルで確認します。`cdg status{:sh}` はプロジェクト全体のキューを表示し、`cdg dag status <ワークフロー>{:sh}` は 1 つのワークフローに含まれる各タスクのステータスを一覧表示します。どちらも、`--watch` を付けると表示が更新され続けます。タスクが具体的に何をしているかを見たいときは、`cdg dag logs{:sh}` または `cdg task logs{:sh}` を使います。タスク間の依存関係は、ワークフローファイルで確認します。[今の状況を確認する：3 つの階層の status](/ja/docs/guides/run-and-monitor#status) を参照してください。

</Accordion>
<Accordion title="ワークフローをスケジュール実行できますか" id="scheduled-runs">

CodeDAG 自体には、スケジュール実行の機能がまだありません。ただし、CodeDAG はコマンドラインツールなので、実行するコンピューターが CodeDAG アカウントにログイン済みで、ネットワークに接続できていれば、cron や launchd のような外部のスケジューラーから `cdg dag submit{:sh}` を直接呼び出して、ワークフローを投入できます。

スケジューラーから呼び出す場合は対話型ターミナルがないため、投入のコマンドに `-y` を付ける必要があります。理由は [cdg dag submit のオプション](/ja/docs/reference/cli/validate-and-submit#options)を参照してください。同じワークフローを繰り返し実行する方法は 2 つあります。1 つは、投入のたびに、先に[前回のレビュー記録をクリアする](/ja/docs/reference/cli/review#clear-and-resubmit)方法で、前回の実行のレビューが終了している必要があります。もう 1 つは、毎回[別のファイル名で投入する](/ja/docs/guides/finish-and-merge#new-file-name)方法で、前回の実行のレビューが終了していなくても投入できます。

</Accordion>
<Accordion title="ワークフローを投入したあとでファイルを変更すると、反映されますか" id="edit-after-submit">

投入済みの実行には反映されません。CodeDAG は投入の時点でワークフローの定義を保存し、その実行は最初から最後まで、保存した定義に従って進みます。変更したファイルが反映されるのは、この実行のレビューが終了し、レビュー記録をクリアして再投入したときです。これは新しい実行になり、タスク数の分のクレジットが改めて消費されます。手順は[投入済みのワークフローを変更する](/ja/docs/reference/cli/validate-and-submit#modify-submitted)を参照してください。あるタスクの方向を修正したいだけなら、ファイルを変更する必要はありません。タスクのセッションに入ってエージェントと直接やり取りするか、レビューのときに修正を依頼します。[監視と修正の方法を選ぶ](/ja/docs/guides/intervene-and-control#choose-intervention)を参照してください。

</Accordion>
</Accordions>

## Git と結果

<Accordions type="single">
<Accordion title="現在のブランチが切り替わっているのはなぜですか" id="current-branch-changed">

デフォルトの分離ブランチモードでは、プライマリリポジトリもワークスペースの 1 つだからです。実行中は、CodeDAG がプライマリリポジトリを、そこに割り当てられたタスクのタスクブランチに切り替えます。ワークフローの終了後、プライマリリポジトリは統合ブランチ `cdg/<ワークフロー名>/integration` をチェックアウトした状態のままで、元のブランチには戻りません。これは想定どおりの動作で、メインブランチそのものは変更されていません。自分で元のブランチに戻す必要があるのはどんなときか、プライマリリポジトリを実行に使わせないようにするにはどうするかは、[プライマリリポジトリのブランチが切り替わっている](/ja/docs/troubleshooting/troubleshooting#branch-switched)を参照してください。

</Accordion>
<Accordion title="結果が main に入っていないのはなぜですか" id="results-not-on-main">

CodeDAG がメインブランチにコミットすることはなく、いつ、どのようにマージするかはユーザーが決めるからです。デフォルトの分離ブランチモードでは、各タスクの変更はそれぞれのタスクブランチに残り、レビューを通った結果は、最後にそのワークフローの統合ブランチ `cdg/<ワークフロー名>/integration` にマージされます。内容を確認したあとは、そのまま main にマージする、プッシュしてプルリクエストを作成する、一部のタスクのブランチだけを選んでマージする、のいずれかを選べます。共有ワークスペースモードにはこれらのブランチがなく、結果は作業ディレクトリにそのまま残るので、確認したうえで自分でコミットします。方法は[仕上げ、マージ、クリーンアップ](/ja/docs/guides/finish-and-merge)を参照してください。

</Accordion>
<Accordion title="git branch に表示される cdg/ で始まるブランチは削除できますか" id="delete-cdg-branches">

できます。ワークフローのレビューが終了し、必要な結果をマージし終えたら、そのワークフローのタスクブランチ、統合ブランチ、スナップショットブランチは、どれも `git branch -D` で削除できます。ただし、スナップショットブランチを削除すると、そこに保存されていた変更はもう取り出せません。まだキューにあるワークフローや、レビューを待っているワークフローのブランチは、CodeDAG がマージとレビューに引き続き使います。こうしたワークフローでは、レビューが終了してからクリーンアップしてください。削除の手順は[ブランチとワークスペースをクリーンアップする](/ja/docs/guides/finish-and-merge#cleanup)を参照してください。

</Accordion>
<Accordion title=".codedag ディレクトリはプロジェクトリポジトリにコミットする必要がありますか" id="commit-codedag-directory">

必要ありません。`.codedag/` はそれ自体が独立した Git リポジトリで、`cdg init{:sh}` の時点で、プロジェクトリポジトリがこのディレクトリを無視するように設定されています。そのため、プロジェクトリポジトリの `git status` には表示されません。ワークフローの履歴を残したい場合や、チームで共有したい場合は、`.codedag/` に移動して、通常の git コマンドでコミットとプッシュをすれば済みます。理由は[サイドカーリポジトリ](/ja/docs/concepts/how-it-works#sidecar-repo)、共有の方法は[チームで共有する](/ja/docs/guides/team-sharing)を参照してください。

</Accordion>
</Accordions>

## レビュー

<Accordions type="single">
<Accordion title="タスクをキャンセルしたら、ブランチが 1 本増えたのはなぜですか" id="cancel-creates-snapshot">

それはスナップショットブランチで、キャンセルされた変更を記録として残すためのものです。分離ブランチモードでは、`cancel` と `defer` のどちらにも、デフォルトで `--code snapshot` が適用されます。タスクに変更がある場合、CodeDAG はまずその変更を `cdg/<ワークフロー名>/snapshots/` で始まるブランチに保存し、それからタスクブランチをタスク開始前の状態に巻き戻します。そのため、これらの変更は下流に渡されません。こうしておけば、あとで考えが変わっても、スナップショットから変更を取り出せます。変更が不要だとわかっている場合は、`--code discard` を付けてそのまま破棄すれば、このブランチは作られません。ワークフローレベルの `cdg dag review cancel{:sh}` も、同じようにデフォルトでスナップショットを残します。スナップショットを残す場合とそのまま破棄する場合の使い分けは [`--code`](/ja/docs/reference/cli/review#code)、スナップショットから取り出す方法は[スナップショットから一部の変更を取り出す](/ja/docs/reference/branches-and-files#restore-from-snapshot)を参照してください。

</Accordion>
<Accordion title="dag review を実行すると、個々のタスクに出したレビューの結論は上書きされますか" id="dag-review-and-task-reviews">

上書きされません。個々のタスクにすでに出した結論は、そのまま変わりません。`dag review` が処理するのは、まだレビューの結論が出ていないタスクだけです。そのうち、すでに実行されたタスクには、今回ワークフロー全体に対して選んだアクションが適用されます。たとえば `cdg dag review accept{:sh}` は、こうしたタスクを承認します。ただし、統合ブランチに最終的に何が残るかは、ワークフローレベルの結論で決まります。分離ブランチモードでは、`dag review cancel` または `defer` を実行すると、統合ブランチが今回のワークフローのベースに戻り、承認済みのタスクの結果も統合ブランチには残りません（デフォルトでは、先にスナップショットが保存されます）。2 つのレベルのレビューの関係は[レビューゲート](/ja/docs/concepts/review-gates#review-gate)、操作は[ワークフロー全体をレビューする：dag review](/ja/docs/guides/review-tasks#dag-review) を参照してください。

</Accordion>
<Accordion title="レビューの結論は取り消せますか" id="undo-review">

取り消せません。`accept`、`cancel`、`defer` は最終的な結論で、いったん出すと、その実行の中では変更できません。承認された結果は、すでに下流のタスクにマージされている可能性もあります。理由は[レビューの結論は変更できない](/ja/docs/concepts/review-gates#no-undo)を参照してください。そのため、タスクにまだ修正を続けさせたい場合は、最終的な結論を出す前に、`revise`、`request-changes`、`rework` のいずれかを使います。これらは結論を出さず、タスクは修正を続けます。アクションの選び方は、[判断に応じてアクションを選ぶ](/ja/docs/guides/review-tasks#choose-action)を参照してください。結論を出したあとで結果の問題に気づいた場合、手直しできるのはコードであって、レビューの結論ではありません。方法は[タスクにレビューの結論が出たあとで問題に気づいた](/ja/docs/troubleshooting/troubleshooting#after-conclusion)を参照してください。

</Accordion>
</Accordions>

## エージェント

<Accordions type="single">
<Accordion title="mode を書かないとどうなりますか" id="mode-omitted">

CodeDAG がタスクに権限モードを指定することはなく、タスクエージェントは自身の設定に従って動作します。たとえば、Claude Code の設定にあるデフォルトの権限モードや、Codex の設定にある許可とサンドボックスの設定です。こうした設定は、ワークフローファイルからは読み取れません。その設定がファイルの変更やコマンドに許可を求めるものであれば、タスクは止まって誰かの応答を待ち、無人実行のワークフローはそこで止まったままになります。そのため、すべてのタスクに `mode` を明記することをおすすめします。書かない場合の具体的な動作は [`mode` を書かない場合](/ja/docs/guides/agents-and-permission-modes#mode-omitted)、選び方は[無人実行か有人実行かを決める](/ja/docs/guides/agents-and-permission-modes#unattended-or-attended)、書き方は[権限モードの構文](/ja/docs/reference/workflow-file#mode-syntax)を参照してください。

</Accordion>
<Accordion title="フルアクセスは安全ですか" id="full-access-safety">

安全とは言えません。フルアクセスは、エージェント自身の権限チェックを手放す代わりに、無人実行を可能にするものです。フルアクセスでは、タスクエージェントはコマンドの実行やファイルの読み書きの前に同意を求めなくなり、CodeDAG が代わりにチェックすることもありません。Claude Code と Codex の公式ドキュメントはどちらも、この種のモードを慎重に使うよう注意を促しています。分離ブランチモードは、コードの変更をタスクブランチにとどめ、メインブランチに触れさせないようにできますが、リポジトリ外のファイル、このコンピューターのほかのリソース、ネットワークへのアクセスまでは制御できません。そのため、フルアクセスが向いているのは、信頼できるリポジトリとタスクです。無人実行でも確認の機会を残したい場合は、手動レビューのノードや検証タスクをワークフローに組み込めます。方法は[無人実行でもゲートは置ける](/ja/docs/guides/agents-and-permission-modes#gates)を参照してください。

</Accordion>
<Accordion title="1 つのワークフローで Claude Code と Codex を組み合わせて使えますか" id="mix-agents">

使えます。タスクごとに、[`agent`](/ja/docs/reference/workflow-file#tasks-agent) フィールドで `claude`（Claude Code）または `codex`（Codex）を個別に選びます。よくある分担は、一方に実装を、もう一方にレビューを任せる形です。`mode` の書き方は 2 つのエージェントで異なるため、組み合わせて使うときは、どのタスクでも、そのタスクのエージェントに合わせて書く必要があります。方法は [Claude Code と Codex を組み合わせる](/ja/docs/guides/mixing-agents)を参照してください。

</Accordion>
<Accordion title="プラグインの一覧にランタイムプラグインが増えているのはなぜですか" id="runtime-plugin">

それは CodeDAG が自動で読み込む内部プラグインで、自分で管理する必要はありません。Claude Code のタスクのセッション（たとえば `cdg task view{:sh}` で入ったセッション）に表示される `codedag-runtime` は、CodeDAG が Claude Code のタスクセッションを起動するたびに一緒に読み込むものです。タスクがいつ完了したかなど、セッションの進み具合を CodeDAG が把握するために使われます。このプラグインがユーザーのプラグイン設定に書き込まれることはなく、普段自分で開くセッションに表示されることもありません。CodeDAG がバージョンに合わせて自動で管理します。これは CodeDAG Guide プラグインとは別のものです。CodeDAG Guide プラグインの管理は、[CodeDAG Guide プラグインを管理する](/ja/docs/guides/guide-plugin)を参照してください。

</Accordion>
</Accordions>

## アカウントとクレジット

<Accordions type="single">
<Accordion title="クレジットはいつ差し引かれますか。投入に成功したのにクレジットが減っていないのはなぜですか" id="when-credits-are-charged">

クレジットは、ワークフローがキューの先頭に来て、実際に実行が始まる直前に差し引かれます。タスク数の分がまとめて差し引かれ、1 タスクにつき 1 クレジットです。投入時に CodeDAG が行うのは、ログイン済みかどうかと、残りのクレジットが足りるかどうかの確認だけで、クレジットは差し引かれません。キューで待っている間も差し引かれません。そのため、前にまだ実行中のワークフローがある場合、投入に成功してもクレジットはすぐには変わらず、順番が来て実行が始まるときに初めて減ります。ルールの全体は、[クレジットが差し引かれるタイミング](/ja/docs/account/credits-and-subscription#when-charged)を参照してください。

</Accordion>
<Accordion title="CodeDAG はコードをアップロードしますか" id="data-uploaded">

アップロードしません。タスクは自分のコンピューターで実行され、CodeDAG サービスが受け取るのは、クレジットの計算と差し引きに必要な情報だけです。具体的には、ワークフローファイルの相対パスと内容（プロンプトを含む）、タスク ID、CLI のバージョン、OS、プロセッサーのアーキテクチャです。リポジトリ内のコードと実行ログは、どちらもアップロードされません。送信のタイミングと内容は、[送信されるデータの範囲](/ja/docs/account/login-and-account#data-boundary)を参照してください。データの取り扱いに関する詳しい説明は、[プライバシーポリシー](/ja/privacy)にあります。

</Accordion>
<Accordion title="Web でログアウトしたのに、CLI を使えるのはなぜですか" id="web-sign-out">

Web コンソールのログインと CLI のログインが、互いに独立しているからです。Web でログアウトしても、終了するのはブラウザーでのセッションだけで、CLI はログインしたままです。このコンピューターの CLI からログアウトするには、`cdg auth logout{:sh}` を実行します。[ログアウト、複数のコンピューター、アカウントの切り替え](/ja/docs/account/login-and-account#sign-out)を参照してください。

</Accordion>
<Accordion title="ブラウザーがない環境では、どうやってログインしますか" id="sign-in-without-browser">

現在のところ、ログインできません。ブラウザーのない環境でのログインは、今後のバージョンで対応する計画に入っています。ログインは、`cdg` を実行するコンピューターのブラウザーで完了させる必要があり、SSH のリモートセッション、コンテナー、GUI のないサーバーではできません。理由と、使えない回避策は、[デスクトップのブラウザーがない場合](/ja/docs/account/login-and-account#no-browser)を参照してください。

</Accordion>
</Accordions>

## プラットフォームとインストール

<Accordions type="single">
<Accordion title="Windows に対応していますか" id="windows">

パブリックベータの期間中は、対応していません。CodeDAG が現在対応しているのは macOS と Linux で、Homebrew でインストールします。[インストールとログイン](/ja/docs/get-started/installation)を参照してください。

</Accordion>
<Accordion title="Node.js をインストールする必要はありますか" id="nodejs">

必要ありません。CodeDAG は単体の実行ファイルとして配布されていて、Homebrew でインストールすれば、そのまま `cdg` を実行できます。[インストールとログイン](/ja/docs/get-started/installation)を参照してください。Claude Code や Codex は、それぞれの方法でインストールします。

</Accordion>
<Accordion title="サーバーやコンテナーで使えますか" id="servers-and-containers">

デスクトップのブラウザーがないサーバーやコンテナーでは、現在のところ使えません。こうした環境での利用は、今後のバージョンで対応する計画に入っています。CodeDAG を使うにはログインが必要で、現在のところ、ログインは同じコンピューターのブラウザーで完了させる必要があるからです。[デスクトップのブラウザーがない場合](/ja/docs/account/login-and-account#no-browser)を参照してください。

</Accordion>
</Accordions>
