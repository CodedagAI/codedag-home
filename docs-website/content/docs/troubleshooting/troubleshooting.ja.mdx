ワークフローが止まったまま動かないときや、タスクがいつまでも進まないときでも、たいていは原因に対処すれば、ワークフローは止まったところから実行を続けます。再投入する必要はありません。状態を表す語そのものの意味は、[状態の意味](/ja/docs/reference/states)を参照してください。

## 症状から探す

| 起きている症状 | 参照する節 |
|---|---|
| タスクがずっと `working` のままで、ログに長い間新しい内容が出ない | [タスクに長時間新しい出力がない](#no-output) |
| タスクまたはワークフローが `on-hold` と表示されている | [タスクまたはワークフローが on-hold で止まっている](#on-hold) |
| タスクが `done` で止まり、そのタスクに依存するタスクがいつまでも開始されない | [タスクが done で止まったまま進まない](#stuck-in-done) |
| キューの後ろに並んだワークフローがいつまでも開始されない | [キューの後ろのワークフローが開始されない](#queue-waiting) |
| タスクが起動直後に止まり、ログの末尾がエージェントの起動画面になっている | [タスクが起動直後に止まる](#agent-start-failed) |
| ログの末尾が、エージェントの確認画面または質問で止まっている | [エージェントが許可または回答を待っている](#approval-waiting) |
| タスクは完了と表示されているのに、あるはずの変更が残っていない | [タスクが「完了」したのに何もしていない](#empty-result) |
| ログに利用上限またはレート制限が表示されている、または理由が `agent-api-error` になっている | [エージェントの利用上限またはレート制限](#agent-usage-limits) |
| コンピューターの再起動またはプロセスのクラッシュのあとも、タスクが `working` と表示されている | [コンピューターの再起動またはプロセスのクラッシュのあと](#after-restart) |
| `cdg dag submit{:sh}` がエラーになり、ワークフローがキューに入らない | [投入が拒否された](#submit-rejected) |
| レプリカを登録したのに、タスクが 1 つずつ順番に実行される | [同時実行数が 1 にしかならない](#concurrency-one) |
| プライマリリポジトリの現在のブランチが変わっている | [プライマリリポジトリのブランチが切り替わっている](#branch-switched) |
| `cdg task view{:sh}` でセッションに入れない、またはキー入力に反応しない | [task view に接続できない、または反応しない](#task-view-problems) |
| `cdg init{:sh}` が失敗する、または設定ファイルに誤りがあると表示される | [初期化と設定](#init-and-settings) |
| ログインに失敗する、または何度もログインし直すよう求められる | [ログインに失敗する、または繰り返しログインを求められる](#sign-in-problems) |
| CLI、Claude Code、プラグインのいずれかのバージョンが合っていないと表示される | [バージョンに関する問題](#versions) |
| タスクが承認、キャンセル、または見送りになったあとで、結果がおかしいことや、結論を誤ったことに気づいた | [タスクにレビューの結論が出たあとで問題に気づいた](#after-conclusion) |
| 同じ問題が繰り返し起こるので、新しいワークフローで仕切り直したい | [ワークフローが途中まで進んだが、続けるのが難しい](#start-over) |
| サポートに問い合わせたい | [サポートを受けるための情報を集める](#get-help) |

## タスクに長時間新しい出力がない [#no-output]

タスクがずっと `working` と表示されているのに、ログに長い間新しい内容が出ないときは、まず、タスクがまだ作業中なのか、ユーザーの応答を待っているのか、すでに止まっているのかを確かめます。

1. `cdg task status <タスク ID> -w <ワークフロー>{:sh}` を実行して、タスクのサブステータスを確認します。`on-hold` と表示されている場合は、[タスクまたはワークフローが on-hold で止まっている](#on-hold)に沿って対処します。`working (stale owner)` と表示されている場合は、タスクを実行していたプロセスがすでに存在しないので、[コンピューターの再起動またはプロセスのクラッシュのあと](#after-restart)に沿って対処します。
2. `cdg task logs <タスク ID> -w <ワークフロー> -n 50{:sh}` を実行して、ログの最後の数十行を確認します。末尾がエージェントの確認画面または質問で止まっている場合は、エージェントが応答を待っています。[エージェントが許可または回答を待っている](#approval-waiting)を参照してください。利用上限またはレート制限のメッセージが出ている場合は、[エージェントの利用上限またはレート制限](#agent-usage-limits)を参照してください。エージェントの起動画面で止まったままで、自分のプロンプトがどこにも見当たらない場合は、[タスクが起動直後に止まる](#agent-start-failed)を参照してください。
3. ログに異常が見当たらなければ、たいていはエージェントがまだ作業中です。タスクに長時間新しい出力がないのはなぜか、どのくらい動きがなければ介入すべきかは、[止まったままかどうかを見分けるには](/ja/docs/guides/run-and-monitor#is-it-stuck)を参照してください。
4. それでも判断がつかないときは、`cdg task view <タスク ID> -w <ワークフロー>{:sh}` でタスクのセッションに入り、様子を直接確認します。必要なら、その場でエージェントにメッセージを送って方向を修正できます。セッションへの入り方と抜け方は、[セッションに入る、修正する、抜ける](/ja/docs/guides/intervene-and-control#task-view)を参照してください。

コマンドがハングして戻ってこないなど、タスクが本当に止まったままだと確認できたら、まず `cdg task kill <タスク ID> -w <ワークフロー>{:sh}` で強制停止するとよいでしょう。強制停止で中断されるのはエージェントの現在の出力だけで、セッションは残ります。そのあと `cdg task recover <タスク ID> -w <ワークフロー>{:sh}` を実行すれば、同じセッションで続きから再開できます。

## タスクまたはワークフローが on-hold で止まっている [#on-hold]

`on-hold` は、CodeDAG が自分では処理できない状況に行き当たり、止まってユーザーの対処を待っていることを表します。対処の手順はいつも同じです。まず理由を確認し、その理由に応じて対処してから、最後に復旧します。

タスクの保留の理由は、タスクを 1 つだけ指定して確認したときにしか表示されません。`cdg task status <タスク ID> -w <ワークフロー>{:sh}` にタスク ID を 1 つだけ書くと、出力に `Reason:` 行が表示されます。理由によっては `Diagnostic:` 行も付き、より具体的な状況と、推奨される対処が示されます。その次の `Docs:` 行は、このページの該当する節へのリンクです。タスク ID を複数書いた場合、出力は一覧だけになり、理由は表示されません。

```bash title="Terminal"
cdg task status 2 -w feature
```

```bash title="Terminal"
[TZ: -04:00] 2026-09-30 10:19:28

Task 2 in .codedag/dags/feature.yaml
Title: ログインAPIを実装
Phase: 📤 submitted
Status: 🔘 pending
Substatus: on-hold
Reason: workspace-dirty
Diagnostic: Task workspace has uncommitted changes: ?? notes.txt
Docs: https://codedag.com/docs/troubleshooting/troubleshooting#hold-workspace
Workspace: /Users/you/my-app
Branch: cdg/feature/t2-ログインapiを実装
```

ワークフローそのものが保留になることもあります。その場合、理由は `cdg dag status <ワークフロー>{:sh}` の出力の冒頭にある `Reason:` 行に表示されます。たとえば `Reason: DAG startup failed (dag-startup-failed)` です。理由によっては同じように `Diagnostic:` 行が付き、最後に `Docs:` 行が続きます。どのタスクが保留になっているかは、同じ出力の各タスクの行に `[pending] [on-hold]` と表示されているかどうかでわかります。

原因に対処したら、タスクは `cdg task recover <タスク ID> -w <ワークフロー>{:sh}` で、ワークフローは `cdg dag recover <ワークフロー>{:sh}` で復旧します。後者は、そのワークフローにある復旧できるタスクもすべて一緒に復旧します。原因が実際には解消されていなければ、タスクやワークフローは再び `on-hold` で止まります。`cdg task view{:sh}` でセッションに入っても、保留は解除されません。セッションの中で対処を終えたあとも、`recover` を実行する必要があります。

### ワークスペースに未コミットの変更または未完了の Git 操作がある [#hold-workspace]

理由が `workspace-dirty` または `git-operation-in-progress` の場合、このタスクに割り当てられたワークスペースがクリーンでないため、CodeDAG はそこでタスクブランチをチェックアウトできません。これが起こるのはデフォルトの分離ブランチモードだけで、未追跡の新しいファイルも変更として扱われます。最もよくあるのは、プライマリリポジトリにまだコミットしていない作業が残っているケースです。プライマリリポジトリは、最初に使われるワークスペースだからです。この状況は、投入時にも CodeDAG が知らせます。

該当するワークスペースで、変更をコミットするか、退避するか（たとえば `git stash -u`）、破棄します。merge、rebase、cherry-pick のいずれかが終わっていない場合は、完了させるか、`--abort` で中止します。そのあと、`cdg task recover{:sh}` または `cdg dag recover{:sh}` を実行します。どのワークスペースかわからないときは、`cdg task status <タスク ID> -w <ワークフロー>{:sh}` の `Workspace:` 行でパスを確認できます。ワークフローの実行中もプライマリリポジトリで開発を続けたい場合は、プライマリリポジトリを実行の対象から外せます。方法は[ワークフローの実行中に自分でも開発を続ける](/ja/docs/guides/parallel-workspaces#keep-main-repo)を参照してください。

このタスクのためにワークスペースを片付けるつもりがない場合は、復旧せずに、そのまま終わらせることもできます。`cdg task review cancel <タスク ID> -w <ワークフロー>{:sh}` または `defer` を実行すると、タスクに結論が出ます。ワークフローレベルでは、`cdg dag review cancel <ワークフロー>{:sh}` または `defer` を使います。こうしたタスクは一度も実行されていないため、レビューはそのコードに手を付けず、ワークスペースの変更も現在のブランチもそのまま残ります。保留になったあと `cdg task kill{:sh}` で止めたタスクも同じです。そのまま終わらせることも、原因に対処してから `recover` を実行することもできます。後者の場合、タスクは準備をやり直して最初から起動されます。

先に片付けなければならないケースが 1 つだけあります。クリーンでないワークスペースが、統合ワークスペースでもある場合です（通常は、ワークスペースが 1 つだけのプロジェクトのプライマリリポジトリです）。この場合、`cdg dag review cancel{:sh}` は `Integration workspace must be clean before DAG publish.` というエラーを出し、何も変更しません。`cdg task review cancel{:sh}` はタスクを終わらせることはできますが、そのあとワークフローが `integration-workspace-dirty` で止まります。

理由が `integration-workspace-dirty` または `integration-git-operation-in-progress` の場合も、状況は同じです。違うのは、すべてのタスクのレビューが終わり、CodeDAG が結果を統合ブランチにマージしようとする時点で起こることと、チェックされるのが統合ブランチのあるワークスペース（通常はプライマリリポジトリ）であることです。片付けてから、`cdg dag recover <ワークフロー>{:sh}` を実行します。

### ブランチの問題 [#hold-branch]

ここに挙げる理由はどれも、CodeDAG がワークスペースを必要なブランチに切り替えられなかったことを表します。最初の 2 つの理由では、タスクはまだワークスペースを準備する段階で止まっています。そのため、[ワークスペースに未コミットの変更がある](#hold-workspace)場合と同じように、原因に対処してから復旧することも、`cdg task review cancel{:sh}` または `defer` でそのまま終わらせることもできます。

- `branch-name-conflict`：タスクがワークフローファイルの [`branchName`](/ja/docs/reference/workflow-file#tasks-branch-name) でブランチ名を指定していて、同じ名前のブランチがすでに存在します。最もよくあるのは、`branchName` を書いたワークフローをもう一度実行した場合です。前回の実行で作られたブランチが残っていますが、CodeDAG がそれを新しい実行に使うことはありません。`cdg task status <タスク ID> -w <ワークフロー>{:sh}` の `Diagnostic:` 行に、ブランチ名を何が占有しているかと、それぞれの対処方法が示されます。

  - **ワークスペースにある同じ名前のローカルブランチ：** 診断にワークスペースのパスが示されます。そのブランチを自分で削除するか、`git branch -m` で名前を変えて残します。
  - **CodeDAG の同期リポジトリが占有しているブランチ名：** clone をレプリカにしている場合、前回の実行で作られたブランチが同期リポジトリにも残っているため、各 clone のローカルブランチを処理するだけでは足りません。プロジェクト内で `cdg branch release <ブランチ名>{:sh}` を実行して解放します。このコマンドは、同期リポジトリからそのブランチを削除し、続いて、各ワークスペースに残っているリモート追跡参照を削除します。

  両方が占有している場合、診断には 2 つとも表示されます。どちらにも対処してから、`cdg task recover{:sh}` を実行します。`cdg branch release{:sh}` は、まだ使われているブランチ名とスナップショットブランチの解放を拒否します。ブランチ名が、キューにあるワークフローの統合ブランチまたはタスクブランチのものである場合は、そのワークフローのレビューが終了するまで待つ必要があります。そのほかのケースは、[cdg branch release](/ja/docs/reference/cli/control#branch-release) を参照してください。同じ名前のブランチについては、投入時の検証でも警告が出ます。警告に従って対処してから投入すれば、タスクがここで止まることはありません。

- `branch-checkout-failed`：タスクブランチのチェックアウトに失敗しました。たとえば、このブランチが別のワークスペースでチェックアウトされている場合です。Git では、同じブランチを 2 か所で同時にチェックアウトすることはできません。そのワークスペースを別のブランチに切り替えてから、`cdg task recover{:sh}` を実行します。
- `integration-branch-checkout-failed`：統合ブランチ `cdg/<ワークフロー名>/integration` が、別のワークスペースでチェックアウトされています。同じように、そのワークスペースを別のブランチに切り替えてから、`cdg dag recover <ワークフロー>{:sh}` を実行します。
- `integration-branch-drifted`：統合ブランチが、CodeDAG が続きを進められない位置に移動されたか、削除されました。たとえば、ワークフローの実行中に、誰かが統合ブランチに別の変更をコミットしたり、統合ブランチをリセットしたりした場合です。統合ブランチを元の位置に戻してから（余分なコミットを取り消し、必要なら `git reflog` で元のコミットを探します）、`cdg dag recover <ワークフロー>{:sh}` を実行します。元に戻せない場合は、[ワークフローが途中まで進んだが、続けるのが難しい](#start-over)に沿って、今回の実行を終わらせます。

### ワークフローが実行を開始できない [#dag-startup]

ワークフローの `Reason:` 行に `DAG startup failed (dag-startup-failed)` と表示されている場合、ワークフローは実行の順番が来たものの、実行の開始に必要なベース、ワークスペース、統合ブランチのいずれかを準備できませんでした。`cdg dag status <ワークフロー>{:sh}` は、`Reason:` の次の行の `Diagnostic:` に、今回の失敗の原因を示します。その内容に当てはまる行を、次の表から探してください。

| `Diagnostic:` | 原因 | 対処方法 |
|---|---|---|
| `Failed to resolve baseRef '<baseRef の値>' to a unique commit.` | [`baseRef`](/ja/docs/reference/workflow-file#base-ref) がコミットに解決できないか、複数のコミットに対応しています。`baseRef` はワークフローの実行開始時に初めて解決され、CodeDAG がリモートブランチを代わりにフェッチすることもありません。そのため、このコンピューターにまだ存在しないブランチ名や、リモートにしかないブランチを書いた場合や、同じ名前のブランチとタグが両方ある場合は、ここで止まります。 | この名前が、ただ 1 つのコミットに解決されるようにします。たとえば、該当するブランチを作成するかフェッチします。 |
| `Failed to resolve DAG base commit from HEAD.` | ワークフローに `baseRef` が書かれていないため、ベースの取得元になるワークスペース（通常はプライマリリポジトリ）の `HEAD` をベースにしようとしましたが、そこにはまだコミットが 1 つもありません。たとえば、作成したばかりで、まだ一度もコミットしていないリポジトリです。 | ワークフローは、既存のコミットから始める必要があります。先に、このリポジトリで最初のコミットを作成してください。 |
| `No available workspace after applying excludeWorkspaces.` | [`excludeWorkspaces`](/ja/docs/reference/workflow-file#exclude-workspaces) が、登録済みのワークスペースをすべて除外しています。このケースは投入時の検証で止められるため、ここで表示されたのであれば、投入のあとで登録済みのワークスペースが減っています。 | `cdg init{:sh}` で、除外されていないワークスペースを少なくとも 1 つ登録します。 |
| `No workspace is available for this workflow:` で始まる | 除外されていないワークスペースのディレクトリが、どれも存在しなくなっています。該当するディレクトリは、括弧内に一覧表示されます。このケースも検証で止められるため、ディレクトリがなくなったのは投入のあとです。 | `cdg init{:sh}` をもう一度実行して、登録済みのワークスペースを更新します。 |
| `Merge in progress.`、`Rebase in progress.`、`Cherry-pick in progress.` のいずれか | 統合ワークスペース（通常はプライマリリポジトリ）で、merge、rebase、cherry-pick のいずれかが終わっていません。 | そのワークスペースで完了させるか、`--abort` で中止します。 |

`Diagnostic:` がこれ以外の内容の場合、たとえば Git コマンドのエラーメッセージがそのまま表示されている場合は、その内容に従って対処します。対処したら `cdg dag recover <ワークフロー>{:sh}` を実行します。ワークフローは、もう一度開始を試みます。

投入済みの実行は、常に投入時点のワークフローの定義に従って進み、ワークフローファイルを変更しても影響を受けません。そのため、`baseRef` そのものを書き間違えていた場合や、`excludeWorkspaces` で除外しすぎていた場合は、今回の実行を終わらせ、ファイルを直してから再投入するしかありません。

```bash title="Terminal"
cdg dag review cancel <ワークフロー>
cdg dag review clear <ワークフロー>
cdg dag submit <ワークフロー>
```

この時点で、このワークフローの CodeDAG クレジットはすでに差し引かれています。再投入は新しい実行になるため、タスク数の分のクレジットが改めて消費されます。ルールは[レビュー記録のクリアと再投入](/ja/docs/reference/cli/review#clear-and-resubmit)を参照してください。

### マージコンフリクト [#hold-merge-conflict]

理由が `merge-conflict`（タスク）または `integration-merge-conflict`（ワークフロー）の場合、CodeDAG が各タスクの結果を自動マージする際にコンフリクトが起き、別に起動されたエージェントセッションが 3 回試みても解決できませんでした。該当するワークスペースで、このマージを自分で完了させる必要があります。自動マージが行われる場面は 2 つあります。1 つは合流タスクの開始前で、上流タスクの結果がそのタスクブランチにマージされます。もう 1 つは、すべてのタスクのレビューが終わったあとで、各タスクの結果が統合ブランチにマージされます。仕組みは[合流ノードでのマージとコンフリクト](/ja/docs/concepts/workspaces-and-branches#merge-and-conflicts)を参照してください。

止まった時点で、CodeDAG はすでにこのマージを打ち切っています。ワークスペースにはエージェントが途中まで編集したファイルが残り、コンフリクトしたファイルはステージされておらず、Git もマージ中の状態ではありません。この状態でそのまま `git add` してコミットしても、できるのは通常のコミットで、マージにはなりません。そのため、復旧したときに、CodeDAG は上流の結果がまだマージされていないと判断します。確実なのは、途中までの変更を破棄し、自分でマージをやり直す方法です。

タスクが `merge-conflict` で止まっている場合は、次のように対処します。

1. `cdg task logs <タスク ID> -w <ワークフロー>{:sh}` でログの末尾を確認します。`Incoming source task:` はマージしようとしていた上流タスクで、`Conflict summary:` の下にコンフリクトしたファイルが一覧表示されます。
2. `cdg task status <タスク ID> -w <ワークフロー>{:sh}` で、作業する場所を確認します。`Workspace:` 行がこのタスクのワークスペース、`Branch:` 行がそのタスクブランチです。上流タスクに対して同じコマンドを実行すると、マージするブランチの名前がわかります。
3. そのワークスペースで途中までの変更を破棄し、上流タスクのブランチをマージし直して、コンフリクトを解決してからコミットします。

   ```bash title="Terminal"
   git reset --hard
   git merge cdg/<ワークフロー名>/t<上流タスク ID>-<タイトル>
   # コンフリクトを解決してから
   git add -A
   git commit
   ```

   自動マージはタスクが作業を始める前に行われるため、`git reset --hard` で破棄されるのは、このマージが残した途中までの変更だけです。`git merge` が、未追跡のファイルが上書きされると表示した場合は、前回のマージが新しく作成したファイルも残っています。先に `git clean -fd` で削除してください。clone のレプリカを使っている場合、上流タスクのブランチは、そのタスクを実行したレプリカにしかなく、`codedag-mirror` リモートにもありません。現在のワークスペースにない場合は、まず、そのタスクを実行したレプリカからフェッチします。たとえば `git fetch ../my-app-clone-1 cdg/<ワークフロー名>/t<上流タスク ID>-<タイトル>{:sh}` を実行し、上の `git merge` の代わりに `git merge FETCH_HEAD{:sh}` を使います。
4. `git status` がクリーンであることを確認してから、`cdg task recover <タスク ID> -w <ワークフロー>{:sh}` を実行します。CodeDAG は、この上流の結果がすでにタスクブランチに入っていることを検出し、残りの上流のマージを続けてから（コンフリクトが起きた場合は、今回もまずエージェントに任せます）、タスク本体を開始します。マージがまだコミットされておらず、マージ中の状態のままだと、タスクは `on-hold` で止まり続けます。

ワークフローが `integration-merge-conflict` で止まっている場合も、手順は同じです。ただし、作業する場所は統合ブランチのあるワークスペースに、マージ先は統合ブランチに変わります。どちらも、`cdg dag status <ワークフロー>{:sh}` の `Integration Workspace:` 行と `Integration Branch:` 行で確認できます。そこで `git reset --hard` を実行し、レビューを通った（`accepted` または `auto-accepted`）タスクのブランチを、コンフリクトが解決するまで 1 つずつマージします。各タスクのレビュー結果は、`cdg dag status <ワークフロー>{:sh}` で確認できます。最後に `cdg dag recover <ワークフロー>{:sh}` を実行すると、まだマージされていない残りの結果は、CodeDAG が続けてマージします。

<Callout type="warn">`git reset --hard` は、そのワークスペースにある未コミットの変更をすべて破棄します。実行する前に、自分で加えた、残しておきたい変更がそのワークスペースにないことを確認してください。判断がつかないときは、先に `git stash -u` で退避しておきます。</Callout>

### エージェントセッションの問題 [#hold-agent-session]

ここに挙げる理由は、タスクエージェントのセッションに問題が起きたか、セッションに渡すはずの内容が届かなかったために、タスクを安全に続行できるかどうかを CodeDAG が判断できないことを表します。ほとんどの場合は、まず `Diagnostic:` 行の説明に従って対処し、それから `cdg task recover{:sh}` を実行します。タスクは、元のセッションで続きから再開します。

| 理由 | 意味 | 対処方法 |
|---|---|---|
| `agent-session-ended` | タスクの実行中に、そのセッションまたは CodeDAG のバックグラウンドプロセスが予期せず終了しました。たとえば、コンピューターが再起動した場合です。 | `cdg task recover{:sh}` を実行します。CodeDAG が元のセッションを開き直し、続きから作業させます。[コンピューターの再起動またはプロセスのクラッシュのあと](#after-restart)を参照してください。 |
| `agent-session-input-unavailable` | セッションが、入力を受け付けられる状態になりませんでした。よくあるのは、応答が必要な画面で止まっているケースです。 | `cdg task view{:sh}` でセッションに入り、その画面に応答してから、セッションを抜けて `cdg task recover{:sh}` を実行します。復旧できない場合は、`cdg task kill{:sh}` でタスクを止めます。 |
| `agent-api-error` | セッションが API エラーで中断されました。最もよくあるのは、利用上限またはレート制限です。 | [エージェントの利用上限またはレート制限](#agent-usage-limits)を参照してください。 |
| `agent-lifecycle-state-unavailable` | セッションがどこまで進んだか、すでに完了しているかどうかを、CodeDAG が確認できません。 | Codex のタスクが起動直後にここで止まった場合は、たいてい、ログインのように人の応答が必要な起動画面で止まっています。[タスクが起動直後に止まる](#agent-start-failed)を参照してください。それ以外の場合は、まず `cdg task recover{:sh}` を実行して再試行します。それでも解決しないときは、`cdg task kill{:sh}` でタスクを止め、変更を確認してから、通常のタスクをレビューするときと同じように結論を出します。Claude Code のバージョンが、CodeDAG で検証済みの範囲より新しい場合にも起こることがあります。[バージョンに関する問題](#versions)を参照してください。 |
| `agent-subagent-incomplete` | Codex のタスクが起動したサブエージェントの中に、まだ終了していないものがあります。 | `cdg task view{:sh}` で確認してから、`cdg task recover{:sh}` を実行します。`Diagnostic:` のサブエージェントに `state=unconfirmed` と示されている場合は、想定外の変更も、残ったままのプロセスもないことを確かめたうえで、[`--acknowledge-unconfirmed`](/ja/docs/reference/cli/control#acknowledge-unconfirmed) を使います。 |
| `agent-worker-liveness-unknown` | 元のワーカープロセスが終了したかどうかを、CodeDAG が確認できません。 | まず `cdg task view{:sh}` で元のセッションに入り、まだ作業中かどうかを確認します。コマンドが `Cannot reach the existing session of task …` というエラーを出した場合は、元のセッションにはもう接続できません。その場合は、[`--force-owner-release`](/ja/docs/reference/cli/control#force-owner-release) の手順に沿って対処します。 |
| `agent-version-unsupported` | Claude Code のバージョンが、CodeDAG がサポートする最低バージョンより古くなっています。 | Claude Code をアップグレードしてから、`cdg task recover{:sh}` を実行します。[バージョンに関する問題](#versions)を参照してください。 |
| `agent-bypass-permissions-unaccepted` | Claude Code のタスクをフルアクセスのモードで実行しようとしていますが、このコンピューターでは、まだこのモードの警告に同意していません。 | 警告に同意してから、`cdg task recover{:sh}` を実行します。方法は [Claude Code のフルアクセスの警告にあらかじめ同意する](/ja/docs/guides/agents-and-permission-modes#accept-bypass-warning)を参照してください。 |
| `continuation-dispatch-failed` | `request-changes` または `rework` で出した依頼を、タスクエージェントに渡せませんでした。 | `cdg task recover{:sh}` を実行します。CodeDAG が、同じ依頼をもう一度送ります。 |

表にない、`agent-` または `codex-` で始まるほかの理由の場合も、対処は同じです。まず `Diagnostic:` を読み、`cdg task view{:sh}` でセッションの様子を確認してから、`cdg task recover{:sh}` を実行します。復旧できない場合は、タスクを止め、[ワークフローが途中まで進んだが、続けるのが難しい](#start-over)に沿って今回の実行を仕上げます。

### 下流が保留になった [#downstream-hold]

理由が `downstream-hold` の場合、レビューでキャンセルまたは見送りを選んだときに `--downstream hold` を指定したため、下流が保留になり、実行するかどうかの判断を待っています。この理由は、タスクにもワークフローにも付くことがあります。`--downstream` に指定できる値は、[レビューのリファレンスの `--downstream` の節](/ja/docs/reference/cli/review#downstream)を参照してください。

保留になっているのがタスクの場合、レビューしたのはその上流タスクです。やはり実行する場合は、`cdg task recover{:sh}` で保留を解除します。タスクは、上流の最新のレビュー結果をもとに待機に戻り、条件が整えば開始されます。もう必要がなければ、`cdg task review cancel{:sh}` または `defer` で終わらせます。

保留になっているのがワークフローの場合、レビューしたのは、キューでその前に並んでいたワークフローです。その後ろに並んでいて、まだ開始されていないワークフローは、すべて `[pending] [on-hold]` で止まります。`cdg status{:sh}` では、それぞれの行の末尾に `(downstream-hold)` と表示され、`cdg dag status <ワークフロー>{:sh}` の `Reason:` 行には `Held by an earlier workflow's review with --downstream hold (downstream-hold)` と表示されます。やはり実行する場合は、`cdg dag recover <ワークフロー>{:sh}` で保留を解除します。このとき、ワークフローを必ず指定してください。コマンドが保留を解除するのは指定したワークフローだけで、残りは保留のままです。ワークフローを省略した場合は、キューの先頭のワークフローだけが対象になります。保留を解除されたワークフローは、キューでの待機に戻り、順番が来ると実行を開始します。もう必要がなければ、`cdg dag review cancel <ワークフロー>{:sh}` または `defer` で終わらせます。

### アカウントとクレジットのチェックで止まった [#startup-gate]

ワークフローの `Reason:` 行に `Startup gate blocked before execution (startup-gate-blocked)` と表示されている場合、ワークフローは実行の順番が来たものの、アカウントとクレジットのチェックを通過できず、まだ実行を開始していません。すぐ下の `Startup gate failure:` 行に具体的な原因が、`Action:` 行に推奨される操作が示されます。

| `Startup gate failure:` | 原因 | 対処方法 |
|---|---|---|
| `insufficient_credits` | 現在の期間の CodeDAG クレジットを使い切っています。 | [クレジット不足またはサブスクリプションがない場合](/ja/docs/account/credits-and-subscription#insufficient-credits)に沿って、使えるクレジットを回復します。 |
| `no_subscription` | アカウントに有効なサブスクリプションがありません。 | 同上。 |
| `login_required` | このコンピューターの CLI がログインしていません。 | `cdg auth login{:sh}` で、このワークフローを投入したアカウントにログインします。 |
| `account_mismatch` | 現在ログインしているのが、このワークフローを投入したアカウントではありません。 | 元のアカウントに切り替えます。[ログアウト、複数のコンピューター、アカウントの切り替え](/ja/docs/account/login-and-account#sign-out)を参照してください。 |
| `billing_service_unavailable` | CodeDAG サービスに一時的に接続できません。 | サービスに接続できるようになるのを待ちます。[サービスを利用できない場合](/ja/docs/account/login-and-account#service-unavailable)を参照してください。 |
| `grant_persist_failed` | クレジットは差し引かれましたが、今回の実行の認可情報をこのコンピューターに保存できませんでした。 | ほかに先に対処することはありません。そのまま復旧します。繰り返し起こる場合は、`Details:` 行に、保存に失敗した具体的な原因が示されています。 |

対処したら `cdg dag recover <ワークフロー>{:sh}` を実行します。ワークフローはもう一度開始を試み、クレジットが二重に差し引かれることはありません。この保留が解除されるまで、`cdg task recover{:sh}` と 2 つの `unpause` コマンドはどれも実行を拒否し、`Workflow is blocked by the startup gate. Run 'cdg dag recover' to resolve it before resuming.` というエラーを出します。このエラーが表示されたら、まず `cdg dag status <ワークフロー>{:sh}` で失敗コードを確認し、上の表に沿って対処してから、ワークフローを復旧します。

失敗コードが `idempotency_replay_expired` または `invalid_usage_grant` の場合、今回の実行に対する課金の認可情報はもう復元できず、`cdg dag recover{:sh}` も実行を拒否します。`Action:` 行に示される 3 つのコマンドで、今回の実行を終わらせてから再投入してください。再投入は新しい実行になり、実行の開始時に、タスク数の分のクレジットが差し引かれます。

### 同期リポジトリが利用できない [#mirror-unavailable]

理由が `mirror-unavailable` の場合、CodeDAG が同期リポジトリの読み書きに失敗しています。clone のレプリカを使っている場合、CodeDAG は、このコンピューター上にある同期リポジトリを介して、ワークスペースの間でブランチを受け渡します。プライマリリポジトリと各 clone にある `codedag-mirror` という名前のリモートが、この同期リポジトリを指しています。

ディスクの空き容量が十分にあるか、CodeDAG のグローバルディレクトリ（デフォルトは `~/.codedag`）に書き込めるか、ワークスペースの `codedag-mirror` リモートが別のアドレスを指すように変更されていないかを確認します。ワークフローが実行の開始時にここで止まった場合は、`cdg dag status <ワークフロー>{:sh}` の `Diagnostic:` 行に、今回のエラーメッセージがそのまま表示されます。多くは Git のエラーで、どの項目を調べるべきかの手がかりになります。リモートが別の場所を指している場合は、そのワークスペースで `git remote remove codedag-mirror{:sh}` を実行して削除します。CodeDAG が、正しいアドレスで追加し直します。対処したら、理由が表示された場所に応じて、`cdg task recover{:sh}` または `cdg dag recover{:sh}` を実行します。

## タスクが done で止まったまま進まない [#stuck-in-done]

タスクが `done` で止まっているのは、実行が終わり、レビューを待っているからです。結論が出るまで、そのタスクに依存する下流のタスクは開始されません。このとき、`cdg dag status <ワークフロー>{:sh}` では、このタスクが `[done] [done]` と表示されます。ワークフローは `[pending] [blocked]` と表示されることがあり、待っているだけのように見えますが、自動的には続行されません。[ワークフローのステータスとサブステータス](/ja/docs/reference/states#shared-substatus)を参照してください。

タスクがここで止まる原因は 2 つあります。

- タスクのレビューポリシーが `none` で、手動レビューが必要です。この設定は、タスクの `autoAccepted`、ワークフローの `taskAutoAccepted`、プロジェクト設定、投入時の `--task-auto-accepted none` のいずれかで指定されたものです。
- タスクが分離ブランチモードで実行され、変更を何も残していません。CodeDAG はこうしたタスクを自動承認せず、`cdg dag status{:sh}` はその行の末尾に `— zero output, awaiting manual review` と表示します。

どちらの場合も対処は同じで、結果を確認してからレビューします。確認に必要な 3 つの情報は、`cdg task status <タスク ID> -w <ワークフロー>{:sh}` でわかります。`Workspace:` はタスクのワークスペース、`Branch:` はそのタスクブランチ、`Base Commit:` はタスク開始前のコミットです。そのため、`git -C <Workspace> diff <Base Commit>{:sh}` を実行すれば、このタスクの変更全体を確認できます。もともと確認するだけでファイルを変更しないタスクのように、結果が想定どおりであれば、`cdg task review accept <タスク ID> -w <ワークフロー>{:sh}` で承認します。下流はすぐに開始されます。変更を残すはずだったのに残していない場合は、`request-changes` で作業を続けさせるか、`rework` でやり直させます。方法は[判断に応じてアクションを選ぶ](/ja/docs/guides/review-tasks#choose-action)を参照してください。自動承認のルールと、ゼロ出力のタスクが自動承認されない理由は、[自動承認](/ja/docs/concepts/review-gates#auto-accept)を参照してください。

レビュー待ちの間に待たされるのは、下流だけではありません。分離ブランチモードでは、`done` で止まっているタスクが自分のワークスペースを占有し続けるため、ほかのタスクが空きワークスペースを得られずに待ち続けることがあります。

設計上ファイルを変更しないタスクを分離ブランチモードで実行する必要がある場合は、結論をあらかじめ決めたファイルに書き出すよう、プロンプトで指示しておく方法があります。こうすれば、ゼロ出力のために止まることはありません。

ワークフロー全体が `[done] [done]` で止まっていて、すべてのタスクのレビューが済んでいる場合は、ワークフローレベルのレビューポリシーが `none`（`dagAutoAccepted: none`）になっています。`cdg dag review accept <ワークフロー>{:sh}` などのコマンドで結論を出してください。

## キューの後ろのワークフローが開始されない [#queue-waiting]

同じプロジェクトのワークフローは、投入した順にキューに並び、一度に実行されるのは先頭の 1 つだけです。そのワークフローのレビューが終了してキューを離れると、次のワークフローが開始されます。そのため、後ろのワークフローが開始されないときは、原因は必ずキューの先頭のワークフローにあります。まず `cdg status{:sh}` で、キューの先頭がどのワークフローで、どの状態にあるかを確認します。

- `[in-progress]`：まだ実行中です。終わるのを待ちます。
- `[done] [done]`、または `[pending] [blocked]` なのに実行中のタスクがない：レビューを待っています。[タスクが done で止まったまま進まない](#stuck-in-done)を参照してください。
- `[stopped] [paused]` または `[stopped] [killed]`：一時停止または強制停止されていて、自動的には続行されません。`cdg dag recover <ワークフロー>{:sh}` で続行させるか、もう必要がなければ、レビューコマンドで終わらせます。
- `[pending] [on-hold]`：保留になっています。[タスクまたはワークフローが on-hold で止まっている](#on-hold)を参照してください。

後ろに並んだワークフロー自身が、止められていることもあります。まだキューで待っているワークフローに `pause` または `kill` を実行していた場合、そのワークフローは順番が来ても開始されず、キューの先頭で止まります。また、前のワークフローをレビューしたときに `--downstream hold` を指定していた場合、後ろに並んだワークフローは `[pending] [on-hold]` と表示され、行の末尾に `(downstream-hold)` が付きます。[下流が保留になった](#downstream-hold)を参照してください。どちらの場合も、`cdg dag recover <ワークフロー>{:sh}` で解除します。

キューの先頭のワークフローを待ちたくない場合は、`cdg dag review cancel <ワークフロー>{:sh}` または `defer` でそのまま終わらせることができます。実行中のタスクが残っているときは、`-k` を付けます。終わらせると、その結果は統合ブランチに残らず、次のワークフローがすぐに開始されます。

## タスクが起動直後に止まる [#agent-start-failed]

エージェントは、通常の入力を受け付ける前に、人の応答が必要な画面を表示することがあります。タスクの起動時にはターミナルの前に誰もいないため、エージェントはその画面で止まります。ディレクトリの信頼についての確認には、CodeDAG が代わりに信頼するほうを選ぶので、タスクが止まることはありません。[CodeDAG が代わりに応答する確認](/ja/docs/guides/agents-and-permission-modes#auto-answered)を参照してください。

次の 2 種類の画面は、ユーザー本人が判断する必要があります。CodeDAG は画面を検出するだけで、代わりにキーを押すことはありません。

- **Claude Code のフルアクセスの警告。** `bypassPermissions`（CodeDAG でのエイリアスは `yolo`）で実行するタスクは、このコンピューターでまだこのモードの警告に同意していない場合、`[pending] [on-hold]` で止まります。理由は `agent-bypass-permissions-unaccepted` で、`Diagnostic:` 行に、ターミナルで警告に同意する方法が示されます。警告に同意してタスクを復旧する手順は、[Claude Code のフルアクセスの警告にあらかじめ同意する](/ja/docs/guides/agents-and-permission-modes#accept-bypass-warning)を参照してください。
- **Codex のログインなど、そのほかの起動画面。** まだログインしていない場合、Codex はログインの案内で止まり、タスクは `[pending] [on-hold]` で止まります。理由は `agent-lifecycle-state-unavailable` です。`Diagnostic:` 行には現在の画面の内容が添えられるので、どの画面で止まっているかを見分けられます。`cdg task view <タスク ID> -w <ワークフロー>{:sh}` でセッションに入り、その中でログインを済ませてから、セッションを抜けて `cdg task recover{:sh}` を実行します。先に `cdg task kill{:sh}` でタスクを止め、ターミナルで `codex{:sh}` を単独で実行して済ませてから、`cdg task recover{:sh}` でタスクを起動し直すこともできます。

エージェントは、CodeDAG が検出できない画面で止まることもあります。この場合、タスクに保留の理由は表示されません。タスクが起動の段階で止まり、ログに自分のプロンプトが見当たらないときは、そのワークスペースでこのエージェントを一度手動で起動し、表示された確認画面に応答してから、`cdg task recover{:sh}` を実行します。

起動画面で止まっているタスクを `kill` で強制停止したあとは、止まった原因に対処してから、そのまま `recover` を実行すれば済みます。今回の実行を終わらせて再投入する必要はありません。こうしたタスクには、再開できるセッションがまだありません。そのため `recover` は、タスクを待機に戻し、準備をやり直して、新しいセッションを起動します。出力には `No recoverable Agent session was established; the task will be prepared and started again.` と表示されます。

## エージェントが許可または回答を待っている [#approval-waiting]

タスクは `working` と表示されているのに、ログの末尾がエージェントの確認画面で止まっていることがあります。たとえば、Claude Code がファイルを作成してよいかを尋ね、その下に `1. Yes`、`3. No` などの選択肢と `Esc to cancel` という案内が並んでいる場合です。これは、タスクエージェントが操作の許可を待っていることを表します。エージェントが質問をして回答を待っているときも、同じように見えます。誰も応答しなければ、エージェントは待ち続けます。

実際のターミナルで `cdg task view <タスク ID> -w <ワークフロー>{:sh}` を実行してセッションに入り、エージェントのネイティブ画面で選択するか、質問に答えます。そのあと Ctrl+C でセッションを抜けると、タスクは実行を続けます。エージェントのシェルツールのように対話型ターミナルのない環境では、この操作に tmux を使う必要があります。オーケストレーションエージェントも、この方法で応答します。[オーケストレーションエージェントが行うこと](/ja/docs/get-started/let-your-agent-orchestrate#what-it-does)を参照してください。

今回の実行では、タスクの権限モードはすでに確定しているため、このあとに出る許可リクエストにも、その都度応答する必要があります。今後のワークフローを無人実行で最後まで進めたい場合は、ワークフローファイルで、各タスクにフルアクセスの `mode` を明記します。たとえば、Claude Code の `bypassPermissions` や Codex の `yolo` です。トレードオフは、[無人実行か有人実行かを決める](/ja/docs/guides/agents-and-permission-modes#unattended-or-attended)を参照してください。フルアクセスであっても、Claude Code は一部の操作については必ず確認を求めます。たとえば、権限ルールで確認が必要と明示的に設定したツール、エージェントが自分からユーザーに投げかける質問、ルートディレクトリやホームディレクトリのような重要なパスの削除です。詳しくは、Claude Code 公式ドキュメントの [Permission modes](https://code.claude.com/docs/en/permission-modes) を参照してください。

## タスクが「完了」したのに何もしていない [#empty-result]

タスクが完了と表示され、場合によっては自動承認までされているのに、あるはずの変更が見当たらないことがあります。分離ブランチモードでタスクブランチに新しいコミットがない、あるいは、書き出すはずだったファイルが存在しないか、中身が空になっている、といった場合です。まず `cdg task logs <タスク ID> -w <ワークフロー>{:sh}` で、エージェントの最後の応答を読みます。作業しなかった理由は、たいていそこに書かれています。

よくある原因は 3 つあります。

- **実行環境にブロックされた。** Codex の `workspace-write` サンドボックスは、デフォルトでネットワークアクセスを禁止しています。そのため、依存関係のインストールやネットワークアクセスが必要なタスクは失敗し、エージェントは完了できないことを報告して終了します。ネットワーク接続が必要な場合は、`mode` に `sandbox=workspace-write,network_access=true` と書きます。書き方は [Codex の権限モードの構文](/ja/docs/reference/workflow-file#mode-codex)を参照してください。
- **権限が足りなかった。** 権限モードまたはサンドボックスが、必要なコマンドの実行や、必要な場所への書き込みを許していない場合も、エージェントは同じように報告して終了します。
- **プロンプトを読んで、することがないと判断した。** たとえば、プロンプトに書かれた対象が見つからなかった場合です。目標、場所、完了条件をより具体的に書きます。[プロンプトを書く：新しいセッションが単独でやり遂げられるようにする](/ja/docs/guides/designing-tasks-and-prompts#write-prompts)を参照してください。

分離ブランチモードでは、変更を何も残さなかったタスクは自動承認されず、`done` で止まってレビューを待ちます。[タスクが done で止まったまま進まない](#stuck-in-done)を参照してください。そのため、「完了したのに何もしていない」という状況は、主に共有ワークスペースモードで起こります。共有ワークスペースモードでは、ゼロ出力のタスクも通常どおり自動承認されます。ステータスの行の末尾に `— zero output` と表示され、タスクのログに警告が 1 件書かれるだけです。同時に実行されているほかのタスクが共有ワークスペースを変更していると、この表示さえ出ないことがあります。

タスクが承認されたあとは、結論を取り消せません。ワークフローファイルの `mode` またはプロンプトを直したうえで、やり残した作業を新しいワークフローに入れます。方法は[承認済みの結果に問題がある](#accepted-result)を参照してください。レビュー記録をクリアして、ワークフロー全体を再投入することもできます。[レビュー記録のクリアと再投入](/ja/docs/reference/cli/review#clear-and-resubmit)を参照してください。

## エージェントの利用上限またはレート制限 [#agent-usage-limits]

長時間実行していると、タスクエージェントが Claude Code または Codex 自体の利用上限（たとえば 5 時間のウィンドウ）に達することがあります。この場合、タスクは `[pending] [on-hold]` で止まり、理由は `agent-api-error` になります。Claude Code のタスクでは、ログに `Claude API stopped the current turn due to rate limiting.` と表示され、そのあとにリセット時刻の情報が続きます。Codex のタスクでは、現在のターンがエラーで終了したことが `Diagnostic:` 行に示されます。

上限の影響を受けるのは、1 つのタスクだけではありません。同じエージェントを使うタスクは、このあと開始されても、すぐに同じ上限に達します。そのため、まず被害を抑え、上限がリセットされてから実行を仕上げます。

1. **被害を抑える。** ワークフローのタスクがすべて同じエージェントを使っている場合や、このあとのタスクがそのエージェントを避けられない場合は、`cdg dag kill <ワークフロー>{:sh}` でワークフロー全体を止めます。実行中のタスクは強制停止されてセッションが残り、まだ開始されていないタスクは `paused` になって、新しいタスクは起動されなくなります。2 つのエージェントを組み合わせていて、もう一方が上限に達していない場合は、上限に達したエージェントのタスクだけを止めます。`cdg task kill <タスク ID...> -w <ワークフロー>{:sh}` には、タスクを一度に複数指定できます。そのうち、まだ開始されていないタスクは `paused` になり、ワークフローのほかのタスクは通常どおり進みます。
2. **上限に達した前後に実行が終わったタスクを確認する。** リセットを待つ間に、上限に達した前後に実行が終わったタスクを見直し、結果に欠けがないことを確認します。結果が不完全なまま承認されたタスクがある場合、その結果はすでに下流に渡されています。対処方法は[承認済みの結果に問題がある](#accepted-result)を参照してください。
3. **復旧する。** 上限がリセットされたら（おおよその時刻は、Claude Code のログにあるリセットの情報でわかります）、`cdg dag recover <ワークフロー>{:sh}` を実行します。`cdg task recover{:sh}` で、止まったタスクだけを復旧することもできます。強制停止されたタスクと保留になったタスクは、元のセッションで続きから再開し、一時停止されたタスクは待機に戻ります。この操作で CodeDAG クレジットが再び消費されることはありません。

同時に実行するタスクが多いほど、エージェントの利用量は速く増え、上限に達しやすくなります。上限に合わせて同時実行数を決める方法は、[同時実行と利用上限](/ja/docs/account/cost-control#concurrency)を参照してください。

## コンピューターの再起動またはプロセスのクラッシュのあと [#after-restart]

CodeDAG は、手元のコンピューターのバックグラウンドプロセスとしてワークフローを実行するため、ターミナルを閉じても影響はありません。しかし、コンピューターが再起動したりプロセスがクラッシュしたりすると、バックグラウンドプロセスも、タスクエージェントのセッションもすべて終了し、ワークフローは自動的には続行されません。

まず `cdg status{:sh}` または `cdg dag status <ワークフロー>{:sh}` で状況を確認します。中断されたタスクは `[in-progress] [working (stale owner)]` と表示されます。出力には `Diagnostic:` 行もあり、どのタスクのワーカープロセスが存在しなくなったかと、復旧するためのコマンドが示されます。`cdg task status <タスク ID> -w <ワークフロー>{:sh}` でタスクを 1 つだけ確認した場合も同じです。タスクによっては、`on-hold` と表示され、理由が `agent-session-ended` になっていることもあります。

案内に従って、ワークフロー全体を復旧します。

```bash title="Terminal"
cdg dag recover <ワークフロー>
```

中断されたタスクは、元のセッションを開き直して続きから再開し、まだ開始されていないタスクは待機に戻ります。キューの後ろに並んだワークフローも、それに続いて順に実行されます。このとき CodeDAG サービスに接続できないと、ワークフローが `on-hold` で止まることがあります。対処方法は[サービスを利用できない場合](/ja/docs/account/login-and-account#service-unavailable)を参照してください。セッションを再開できないタスクがある場合は、そのタスクを止め、[ワークフローが途中まで進んだが、続けるのが難しい](#start-over)に沿って今回の実行を仕上げます。

キューと各タスクの状態は、CodeDAG のグローバルディレクトリ（デフォルトは `~/.codedag`）に保存されています。そこにあるファイルを手作業で変更すると、キューを復旧できなくなるおそれがあります。状態がおかしいときは、`recover`、`kill`、レビューコマンドで対処してください。

## 投入が拒否された [#submit-rejected]

`cdg dag submit{:sh}` が失敗した場合、ワークフローはキューに入らず、クレジットも消費されません。出力されたメッセージに当てはまる行を、次の表から探してください。

| 出力されるメッセージ | 原因 | 対処方法 |
|---|---|---|
| `✗ Validation failed`。その下に `[種類] 説明` の形式の項目が並ぶ | ワークフローファイルに誤りがあります。 | 説明に従って、1 件ずつ修正します。出力の読み方は[「ワークフローファイルを書く」の検証の節](/ja/docs/guides/writing-workflows#validate)、フィールドの書き方は[ワークフローファイルリファレンス](/ja/docs/reference/workflow-file)を参照してください。 |
| `[unsupported-location]` | ファイルが `.codedag/dags/` ディレクトリの下にありません。 | ファイルを `.codedag/dags/` またはそのサブディレクトリに移動します。[ファイルの置き場所と形式](/ja/docs/reference/workflow-file#file-location)を参照してください。 |
| `uses unavailable agent` | プロジェクト設定の `availableAgents` が使えるエージェントを制限していて、タスクが指定したエージェントがその中に含まれていません。エラーメッセージに、このフィールドがどの設定ファイルにあるかが示されます。 | エラーメッセージの案内に従って、そのファイルの [`availableAgents`](/ja/docs/reference/settings#available-agents) にこのエージェントを追加するか、フィールドごと削除します。 |
| `[agent-not-installed]`。説明に `is not installed on this machine` と表示される | タスクが使うエージェントがこのコンピューターにインストールされておらず、`claude` または `codex` コマンドが `PATH` にありません。エラーメッセージの `Used by:` に、そのエージェントを使うタスクが一覧表示されます。分離ブランチモードでマージコンフリクトを処理するエージェントは、`mergeConflictAgent` と表示されます。 | エージェントをインストールし、同じターミナルで直接実行できることを確認します。または、該当するタスクを、インストール済みのエージェントを使うように変更します。そのエージェントがプロジェクトのデフォルトのエージェントでもある場合は、このコンピューターでデフォルトのエージェントを変更する方法も、エラーメッセージに示されます。 |
| `[workspace-not-found]` | このワークフローが使う登録済みのワークスペースのディレクトリが、存在しなくなっています。すべて存在しない場合はエラーになります。一部だけが存在しない場合は警告になり、ワークフローは残りのワークスペースで通常どおり実行されます。 | `cdg init{:sh}` をもう一度実行して、登録済みのワークスペースを更新します。[CodeDAG に登録する](/ja/docs/guides/parallel-workspaces#register)を参照してください。 |
| `Submit anyway?` または `Submission cancelled` | 検証は通りましたが警告があり、確認が必要です。 | 警告の内容を確かめてから確認するか、`-y` を付けて自動的に確認します。明示的に指定した `branchName` が既存のブランチと衝突するという警告の場合は、対話型ターミナルがないと、投入がそのままキャンセルされます。 |
| `[duplicate] Workflow already in queue` | 同じワークフローファイルが、すでにキューにあります。 | 実行が終わり、レビューが終了するのを待ちます。投入済みの実行を変更したい場合は、[投入済みのワークフローを変更する](/ja/docs/reference/cli/validate-and-submit#modify-submitted)を参照してください。 |
| `is in reviewed phase, not planning` | このワークフローの前回の実行は、すでにレビューが終了しています。 | 案内に従って、先に `cdg dag review clear <ワークフロー>{:sh}` を実行してから投入します。これは新しい実行になり、クレジットが改めて消費されます。 |
| `Workflow has review snapshot state`。複数のワークフローを一度に投入した場合は `[review-snapshot]` と表示される | ワークフローに、個々のタスクのレビュー記録が残っています。投入する前に、`cdg task review{:sh}` の `accept`、`cancel`、`defer` のいずれかで、その中のタスクをレビューしていた場合です。 | 案内に従って、先に `cdg dag review clear <ワークフロー>{:sh}` を実行してその記録をクリアしてから、投入します。ルールは[まだ投入していないワークフローにあるタスクのレビュー記録](/ja/docs/reference/cli/review#unsubmitted-task-reviews)を参照してください。 |
| `Not enough credits for this submission.` または `No active paid subscription found for this account.` | クレジットが足りないか、有効なサブスクリプションがありません。 | [クレジット不足またはサブスクリプションがない場合](/ja/docs/account/credits-and-subscription#insufficient-credits)を参照してください。 |
| `Sign-in failed:` | 投入にはログインが必要ですが、ログインが完了しませんでした。 | [ログインに失敗する、または繰り返しログインを求められる](#sign-in-problems)を参照してください。 |
| `Precheck failed:` | 投入の前に CodeDAG サービスでクレジットを確認する際に、エラーが起きました。コロンのあとに、今回の原因が表示されます。 | サービスに接続できない場合や、サービス側でエラーが起きた場合は、サービスを利用できるようになってから、もう一度投入します。[サービスを利用できない場合](/ja/docs/account/login-and-account#service-unavailable)を参照してください。サービス側がリクエストを拒否した場合（たとえば、ワークフローの内容がサービス側の制限を超えている場合）は、そのまま再試行しても結果は変わりません。エラーメッセージに示された、サービス側の原因に対処してから投入します。確認の途中でログインし直す必要が生じ、そのログインが完了しなかった場合は、[ログインに失敗する、または繰り返しログインを求められる](#sign-in-problems)を参照してください。 |

## 同時実行数が 1 にしかならない [#concurrency-one]

タスクが 1 つずつ順番に実行される場合は、次の順に確認します。前の項目が解決してから、次の項目に進んでください。

- **タスクの間に依存関係がある。** 同時に実行できるのは、互いに依存しないタスクだけです。まず、ワークフローの依存関係が、実際に並列実行できる形になっていることを確認します。
- **使えるワークスペースが足りない。** デフォルトの分離ブランチモードでは、同時に実行するタスクごとにワークスペースが 1 つ必要です。プライマリリポジトリが 1 つ分で、残りは登録したレプリカでまかないます。プライマリリポジトリしか登録していなければ、同時実行数は 1 です。[レプリカを準備](/ja/docs/guides/parallel-workspaces#prepare-replicas)して、`cdg init{:sh}` で登録してください。ワークフローの [`excludeWorkspaces`](/ja/docs/reference/workflow-file#exclude-workspaces) で除外したワークスペースも、数に含まれません。
- **`maxConcurrency` が更新されていない。** 同時実行数の上限には、ワークフローファイルの [`maxConcurrency`](/ja/docs/reference/workflow-file#max-concurrency) が使われます。書かれていなければプロジェクト設定の値が使われ、どちらにもなければ 1 になります。`cdg init{:sh}` を初めて実行したときは、レプリカの数に 1 を加えた値が書き込まれます。レプリカを追加したあとで `cdg init{:sh}` をもう一度実行すると、有効な上限がワークスペースの数より小さい場合に、新しい数に変更するかどうかを尋ねられます。デフォルトでは変更されます。`--max-concurrency{:sh}` を指定して、直接書き込むこともできます。上限がチームの共有設定 `.codedag/settings.jsonc` にしか書かれていない場合、初期化はそれをチームが決めた値として扱い、尋ねません。尋ねられたときに変更しないことを選んだ場合や、チームの値とは別の値を使いたい場合は、ワークフローファイルに `maxConcurrency` を書くか、`.codedag/local/settings.local.jsonc` を変更します。[プロジェクト設定の `maxConcurrency`](/ja/docs/reference/settings#max-concurrency) を参照してください。
- **開始済みのタスクがワークスペースを占有している。** 分離ブランチモードでは、タスクは開始されてからレビューが終わるまで、自分のワークスペースと同時実行枠を占有し続けます。`done` で止まってレビューを待っているタスクも、一時停止または強制停止されたタスクも同じです。そのタスクを最後まで実行させてレビューするか、`cdg task review cancel{:sh}` または `defer` で終わらせると、ワークスペースが空きます。

プロジェクト設定は投入時に読み込まれるため、設定の変更は、それ以降に投入するワークフローにだけ反映されます。共有ワークスペースモードではレプリカは不要で、同時に実行されるタスクの数は `maxConcurrency` だけで決まります。

## プライマリリポジトリのブランチが切り替わっている [#branch-switched]

デフォルトの分離ブランチモードでは、これは想定どおりの動作です。プライマリリポジトリもワークスペースの 1 つなので、実行中、CodeDAG はプライマリリポジトリを、そこに割り当てたタスクのブランチに切り替えます。ワークフローが終了すると、プライマリリポジトリは統合ブランチ `cdg/<ワークフロー名>/integration` をチェックアウトした状態で残り、元のブランチには戻されません。メインブランチそのものは変更されていません。理由は[タスクブランチ、統合ブランチ、ベース](/ja/docs/concepts/workspaces-and-branches#branches)を参照してください。

ワークフローの終了後にメインブランチへ戻りたいときは、自分で `git checkout main` を実行します。この操作で、次のワークフローがどこから始まるかも決まります。メインブランチに戻さず、ワークフローファイルに `baseRef` も書いていない場合、次のワークフローは、この統合ブランチの結果の続きから始まります。

ワークフローの実行中もプライマリリポジトリで開発を続けたい場合は、ワークフローファイルに `excludeWorkspaces: ["."]` と書きます。こうすると、タスクはレプリカだけで実行されます。ただし、レプリカを少なくとも 1 つ登録している必要があります。方法は[ワークフローの実行中に自分でも開発を続ける](/ja/docs/guides/parallel-workspaces#keep-main-repo)を参照してください。共有ワークスペースモードではブランチが作られず、プライマリリポジトリのブランチが切り替えられることもありません。

## task view に接続できない、または反応しない [#task-view-problems]

`cdg task view{:sh}` は、現在のターミナルをタスクエージェントのネイティブセッションに接続します。そのため、ターミナルの環境と、タスクがどの段階にあるかの両方に条件があります。起きている状況に応じて対処してください。

- **画面が崩れる、またはキー入力に反応しない。** コマンドが、実際の対話型ターミナルで実行されていません。たとえば、スクリプト、CI、エージェントのシェルツールの中で実行している場合です。実際のターミナルに切り替えるか、tmux の中で実行します。
- **`Task has not started yet.` と表示される。** タスクには、入れるセッションがまだありません。開始を待っているか、開始前の理由（ワークスペースがクリーンでない、ブランチの問題など）で保留になっているか、一度も起動されないまま一時停止または強制停止されています。開始されるのを待つか、[タスクまたはワークフローが on-hold で止まっている](#on-hold)に沿って、保留の原因に対処します。
- **`Session ID not found. Please provide --session-id` と表示される。** セッションはすでに終了していて、コマンドはそれを開き直そうとしましたが、セッション ID が記録されていません。エージェント自身の記録からセッション ID を探し、`--session-id` で指定します。書き方は [cdg task view](/ja/docs/reference/cli/control#task-view) を参照してください。
- **`Session socket not found` または `Connection refused` と表示される。** コマンドが、今はタスクのセッションに接続できません。たとえば、タスクが開始されたばかりで、セッションの準備がまだできていない場合です。少し待ってから、もう一度試してください。それでも接続できないときは、`cdg task status{:sh}` でタスクがすでに止まっていないかを確認し、その状態に応じて対処します。

タスクがすでに強制停止されていて、そのセッションも動いていない場合、セッションに入るには、先にタスクを復旧する必要があります。コマンドはまずこの点を説明してから、復旧するかどうかを尋ねます。デフォルトでは復旧せず、Yes を選んだときだけ、復旧して接続します。質問に答えられる対話型ターミナルがない場合（たとえば、エージェントのシェルツールの中で直接実行している場合）、コマンドはエラーを出して終了コード 1 で終了します。この場合に復旧するには、`--recover` を付けます。タスクが何をしたかを確認したいだけなら、`cdg task logs{:sh}` でログを読みます。

セッションから抜けるには Ctrl+C を押します。タスクはそのまま実行を続けます。やり取りが済んだら、早めにセッションから抜けてください。接続したままにしていると、タスクがいつまでも通常の流れで終了できないことがあります。[セッションに入る、修正する、抜ける](/ja/docs/guides/intervene-and-control#task-view)を参照してください。

## 初期化と設定 [#init-and-settings]

- **`cdg init{:sh}` が `Neither CLI was detected on this machine.` と表示する。** CodeDAG が、現在のターミナルの `PATH` から `claude` も `codex` も見つけられません。先に Claude Code または Codex をインストールし、同じターミナルで直接実行できることを確認してから、`cdg init{:sh}` をもう一度実行します。
- **`cdg init{:sh}` をもう一度実行すると、`File conflicts detected.` と表示され、既存のファイルをどう扱うかを尋ねられる。** 自分で変更した内容を残したい場合は、残す（Keep）を選びます。初期化テンプレートに戻したい場合は、置き換える（Overwrite）を選びます。`.codedag` リポジトリにコミット済みのファイルは自動的に残され、質問の対象になりません。各選択肢の意味は、[1 つずつ尋ねられるときの 6 つの選択肢](/ja/docs/reference/cli/init#file-conflicts)を参照してください。
- **clone のレプリカで `cdg init{:sh}` を実行した。** その clone がすでにいずれかのプロジェクトのレプリカとして登録されている場合、CodeDAG はそれを検出し、質問の前にその旨を表示します。そのうえで、そのプロジェクトのプライマリリポジトリを対象に初期化を続け、レプリカに `.codedag/` は作成しません。まだ登録されていない clone は、独立した新しいプロジェクトとして扱われます。これは正常な動作です。レプリカとして使いたい場合は、プライマリリポジトリに戻って `cdg init{:sh}` を実行し、登録します。[どのディレクトリで実行するか](/ja/docs/reference/cli/init#where-to-run)を参照してください。
- **`Failed to parse project settings file` または `Invalid project settings file` と表示される。** 設定ファイル `.codedag/settings.jsonc` または `.codedag/local/settings.local.jsonc` が正しい JSONC になっていないか、いずれかのフィールドの値が不正です。出力の `Location:` と `Reason:` に従って、ファイルを修正します。設定ファイルでフィールド名のつづりを間違えても、エラーにはならず、そのまま無視されます。設定を変更したのに効果がないときは、まずフィールド名を確認してください。[ファイル形式と、書き間違えた場合の動作](/ja/docs/reference/settings#format)を参照してください。

## ログインに失敗する、または繰り返しログインを求められる [#sign-in-problems]

- **`Sign-in failed:` と表示される、または `cdg auth status{:sh}` が `Failed to show auth status:` と表示する。たとえば、タイムアウトした場合、ブラウザーで認可を拒否した場合、サービスに接続できない場合です。** もう一度実行すれば済みます。`cdg init{:sh}` または `cdg dag submit{:sh}` から始まったログインが失敗した場合は、元のコマンドも終了するため、そのコマンドを実行し直す必要があります。
- **`Configured URL is not an approved CodeDAG auth endpoint.` と表示される。** 現在のターミナルに、環境変数 `CODEDAG_AUTH_BASE_URL` が設定されています。CLI が接続するのは `https://app.codedag.com` だけで、この変数に値が入っているかぎり、ログインも、ログインが必要なコマンドも、すべてこのエラーで終了します。変数を解除してから（`unset CODEDAG_AUTH_BASE_URL{:sh}`）、もう一度実行してください。
- **`Failed to save credentials to the local secure storage.` と表示される。** ブラウザーでのログインは完了しましたが、認証情報をこのコンピューターに保存できなかったため、今回のログインは有効になっていません。CodeDAG のグローバルディレクトリ（デフォルトは `~/.codedag`）に書き込めることと、ディスクの空き容量が十分にあることを確認してから、ログインし直してください。
- **SSH のリモートセッション、コンテナー、GUI のないサーバーでログインできない。** ログインは、`cdg` を実行しているのと同じコンピューターのブラウザーで完了させる必要があるため、こうした環境では現在のところログインできません。[デスクトップのブラウザーがない場合](/ja/docs/account/login-and-account#no-browser)を参照してください。こうした環境への対応は、今後のバージョンの計画に入っています。
- **しばらくすると、ログインし直すよう求められる。** ログイン状態は、長い間使わないと無効になります。また、認証情報を別のコンピューターにコピーして使うと、このアカウントのログインが、すべてのコンピューターでまとめて無効になります。[ログイン状態の有効期間](/ja/docs/account/login-and-account#credentials)と[ログアウト、複数のコンピューター、アカウントの切り替え](/ja/docs/account/login-and-account#sign-out)を参照してください。
- **ログインすると、別のアカウントになっている。** ブラウザーの Web コンソールが別のアカウントでログインしたままになっていると、CLI のログインにはそのアカウントがそのまま使われます。[ログアウト、複数のコンピューター、アカウントの切り替え](/ja/docs/account/login-and-account#sign-out)を参照してください。
- **キューで待っているワークフローが、ログイン状態のために `on-hold` で止まった。** [アカウントとクレジットのチェックで止まった](#startup-gate)を参照してください。
- **CodeDAG サービスを一時的に利用できない。** [サービスを利用できない場合](/ja/docs/account/login-and-account#service-unavailable)を参照してください。

## バージョンに関する問題 [#versions]

**CodeDAG CLI のバージョンが古い。** CodeDAG サービスは、CLI に最低バージョンの要件を設けています。バージョンが古すぎると、サービスへの接続が必要な操作で、アップグレードするよう案内されます。`brew upgrade codedag{:sh}` でアップグレードしてから、もう一度試してください。[インストールとログイン](/ja/docs/get-started/installation)を参照してください。

**Claude Code のバージョンが古い。** CodeDAG がサポートする Claude Code の最低バージョンは 2.1.196 です。このコンピューターに Claude Code がインストールされていることを検出すると、`cdg init{:sh}` はそのバージョンを確認します。バージョンが古すぎる場合や、バージョン番号を取得できない場合は警告を出しますが、初期化は通常どおり完了します。この警告を無視すると、問題はタスクの実行時に表面化します。タスクは `on-hold` で止まり、理由は `agent-version-unsupported` で、ログには `Claude CLI <バージョン> is unsupported for reliable lifecycle detection.` と表示されます。`claude update{:sh}` でアップグレードしてから、`cdg task recover{:sh}` を実行します。復旧のときにもバージョンがサポートされていないと表示される場合は、現在のターミナルの `claude` がまだ古いバージョンのままです。

**Claude Code のバージョンが検証済みの範囲より新しい。** CodeDAG は Claude Code 2.1.292 まで検証済みで、それより新しいバージョンでも通常は問題なく動作します。まれに、タスクが完了したかどうかを CodeDAG が判定できず、タスクが `agent-lifecycle-state-unavailable` で止まることがあります。このとき、ログには、バージョンが検証済みの範囲より新しいことが示されます。作業はたいてい完了していて、失われてはいません。[エージェントセッションの問題](#hold-agent-session)にある、この理由の対処方法に沿って対処してください。Claude Code のバージョンを固定するか元に戻す、または CodeDAG をアップグレードする方法もあります。

**CodeDAG Guide プラグインと CLI のバージョンが合っていない。** `cdg plugin status{:sh}` を実行し、出力の `Action:` 行の案内に従って操作します。通常は、そこに示された `cdg plugin update{:sh}` コマンドを実行します。[プラグインを更新する](/ja/docs/guides/guide-plugin#update)を参照してください。プラグインと CLI の互換性のルールは、[バージョンの互換性](/ja/docs/reference/cli/plugin#compatibility)を参照してください。

## タスクにレビューの結論が出たあとで問題に気づいた [#after-conclusion]

タスクが承認、キャンセル、または見送りになったあとで、結果がおかしいことや、結論を誤ったことに気づく場合があります。最終的な結論は、自分で出したものでも自動承認によるものでも、今回の実行の中では変更できません。理由は[レビューの結論は変更できない](/ja/docs/concepts/review-gates#no-undo)を参照してください。あとから手直しできるのはコードの結果であって、レビューの結論ではありません。分離ブランチモードでは、タスクの変更はすべてブランチに残っています。今回の実行が終了するのを待ってから、Git で処理し、新しいワークフローで続きを進めます。

Git の操作は、今回の実行が終了してから行ってください。実行中、下流が受け取るのは、上流に結論が出た時点の結果です。そのあとで上流のタスクブランチを変更しても、下流には渡りません。また、統合ブランチを変更すると、ワークフローが止まったり、レビューがエラーになったりします。共有ワークスペースモードにはこうしたブランチがなく、タスクが書いたファイルはワークスペースに残ったままです。ワークフローの終了後に、直接修正するか、Git で取り消せば済みます。

### 承認済みの結果に問題がある [#accepted-result]

ワークフローがまだ実行中の場合は、まず、最後まで実行させるかどうかを決めます。まだ終わっていないタスクがこの結果に依存していなければ、そのまま最後まで実行させます。どれもこの結果を前提にしているなら、実行を続けても無駄になります。その場合は、すぐにワークフローを止め、完了済みの結果を確保します。手順は[ワークフローが途中まで進んだが、続けるのが難しい](#start-over)を参照してください。

実行が終了したら、問題の性質に応じて、そのタスクの変更を処理します。

| 状況 | 対処方法 |
|---|---|
| 今の結果に手を加えれば直せる | 手作業で修正するか、新しいワークフローに、不足を補うタスクを入れる |
| 取り消す必要があり、後続のタスクはその結果の上でそれほど変更していない | 統合ブランチで、そのタスクのコミットを取り消す |
| 取り消す必要があり、後続のタスクがどれもその結果を前提にしている | その結果を含まないブランチを別に組み立て、そのタスクと下流を新しいワークフローに入れてやり直す |

コミットの取り消しは、統合ブランチで行います。ワークフローの終了後、プライマリリポジトリはこのブランチをチェックアウトした状態になっています。タスクのコミットは、通常、タスクのタイトルがコミットメッセージになっているコミットです。

```bash title="Terminal"
git log --oneline --no-merges main..cdg/<ワークフロー名>/integration
git revert <コミット>
```

後続のタスクがすでにその結果の上で多くの変更を加えている場合、取り消しはコンフリクトしやすく、後続のタスクの古い結果も統合ブランチに残ったままになります。この場合は、代わりにブランチを別に組み立てます。各タスクブランチに含まれるのは、そのタスクと上流の結果だけです。そのため、今回のワークフローのベースから新しいブランチを作り、問題のタスクに依存しないタスクのブランチをマージすれば、そのタスクと下流を除いた結果が得られます。

```bash title="Terminal"
# 今回のワークフローのベースから新しいブランチを作る。ここでのベースは main
git checkout -b <新しいブランチ> main
# 問題のタスクに依存しないタスクブランチを 1 つずつマージする
git merge cdg/<ワークフロー名>/t<タスク ID>-<タイトル>
```

タスクブランチを一覧表示する方法と、clone のレプリカで実行されたタスクのブランチがどこにあるかは、[一部のタスクの結果だけを取り込む](/ja/docs/guides/finish-and-merge#pick-tasks)を参照してください。

あとから実行するタスクと、やり直すタスクは、新しいワークフローに書き、処理を済ませた結果から始めさせます。統合ブランチで処理した場合の書き方は、[一部のタスクだけをあとから実行する](/ja/docs/guides/finish-and-merge#continue-remaining)を参照してください。ブランチを別に組み立てた場合は、新しいワークフローに `baseRef: <新しいブランチ>` と書きます。結果をまるごと使わない場合は、ブランチを整理する必要はありません。レビュー記録をクリアして、ワークフロー全体を再投入します。[もう一度実行する](/ja/docs/guides/finish-and-merge#run-again)を参照してください。

### タスクを誤ってキャンセルまたは見送りにした [#ended-by-mistake]

キャンセルまたは見送りにしたタスクの変更は、デフォルトでスナップショットブランチに保存されていて、失われてはいません。ただし、今回の実行の下流は、その変更を受け取れません。下流が受け取るのは、このタスクの上流の結果だけです。そのとき `--downstream hold` で保留にした下流も、保留を解除したあとは同じです。そのため、この結果がまだ必要な下流は、保留を解除せずに、同じようにキャンセルするか見送りにします。ワークフローのレビューが終了してから、変更をスナップショットブランチから統合ブランチに取り出します。[必要な部分を取り出す](/ja/docs/reference/branches-and-files#restore-changes)を参照してください。そのうえで、該当する下流を新しいワークフローに書きます。この変更がないまますでに実行が終わった下流をやり直すかどうかは、前の節に沿って判断します。

## ワークフローが途中まで進んだが、続けるのが難しい [#start-over]

実行をその場で直すのが難しくなったときは、手直しを続けるよりも、完了済みの結果を確保し、残りを新しいワークフローで続けるほうがよいでしょう。この方法が向いているのは、次のような場合です。同じ原因が、対処しても繰り返し現れる場合。ワークスペースを手作業で変更しすぎて、どれがタスクの結果なのか区別できなくなった場合。ワークフローの分割やプロンプトそのものに問題があるものの、投入済みの実行は投入時点の定義どおりにしか進められない場合。そして、承認済みの結果に問題があり、まだ終わっていないタスクがどれもその結果を前提にしている場合です。

分離ブランチモードでは、次の手順で仕上げられます。

1. `cdg dag kill <ワークフロー>{:sh}` でワークフローを止めます。実行中のタスクは、すぐに強制停止されます。先に現在のターンを終えさせたい場合は、代わりに `cdg dag pause <ワークフロー>{:sh}` を使い、ワークフローが `in-progress` と表示されなくなるまで待ちます。
2. すでに開始されていて、まだレビューの結論が出ていないタスクを、1 つずつ確認します。結果が不完全なタスクは、`cdg task review cancel <タスク ID> -w <ワークフロー> --downstream cascade{:sh}` でキャンセルします。デフォルトでは、タスクがそれまでに加えた変更はスナップショットブランチに保存されるので、あとから取り出せます。その結果は下流に渡されず、まだ開始されていない下流タスクも、今回の実行ではもう開始されません。
3. `cdg dag review accept <ワークフロー>{:sh}` で、ワークフロー全体を終わらせます。実行が終わっている残りのタスクも一緒に承認され、レビューを通った結果は統合ブランチ `cdg/<ワークフロー名>/integration` にマージされます。プライマリリポジトリは、このブランチをチェックアウトした状態になります。一度も開始されなかったタスクには、レビュー結果が付きません。
4. 残りの作業と、先ほどキャンセルしたタスクを新しいワークフローに書いて、投入します。プライマリリポジトリは統合ブランチをチェックアウトしているので、`baseRef` を書いていない新しいワークフローは、その結果の続きから始まります。`baseRef: cdg/<ワークフロー名>/integration` と書いて、明示的に指定することもできます。新しいワークフローは、タスク数の分の CodeDAG クレジットを別途消費します。

手順 3 では、実行済みでまだ結論が出ていないタスクがすべて承認されます。そのため、結果が不完全なタスクは、手順 2 ですべて処理しておいてください。すでに承認されたタスクの結果に問題がある場合、その変更は統合ブランチに入ります。新しいワークフローを投入する前に、[承認済みの結果に問題がある](#accepted-result)に沿って対処してください。そのあとで結果をメインブランチにマージする方法は、[メインブランチにマージする](/ja/docs/guides/finish-and-merge#merge)を参照してください。

今回の実行の結果がどれも要らない場合は、代わりに `cdg dag review cancel <ワークフロー>{:sh}` で終わらせます。統合ブランチは、今回の実行のベースに戻ります。共有ワークスペースモードには、タスクブランチも統合ブランチもありません。すでに加えられた変更はそのままワークスペースに残るので、ワークフローを終わらせてから、新しいワークフローで続きを進めれば済みます。

## サポートを受けるための情報を集める [#get-help]

このページに沿って調べても問題が解決しない場合は、次の情報をまとめたうえで、私たちにお知らせください。

- `cdg --version{:sh}` の出力、使っているエージェントのバージョン（`claude --version{:sh}` または `codex --version{:sh}`）、OS。
- 問題が起きているワークフローの `cdg dag status <ワークフロー>{:sh}` の出力。
- 問題が起きているタスクの `cdg task status <タスク ID> -w <ワークフロー>{:sh}` の出力。なかでも `Reason:` と `Diagnostic:` が最も重要です。
- そのタスクのログの末尾。たとえば `cdg task logs <タスク ID> -w <ワークフロー> -n 100{:sh}` の出力です。
- 問題が起きる前に実行したコマンドと、ワークフローファイルのうち問題に関係する部分。

ログにはタスクエージェントの出力が含まれ、コード、パス、シークレットが入っていることがあります。送る前に一度確認し、外部に出すべきでない内容は削除してください。

まとめた情報は、メールで <Email user="hi" /> までお送りください。公開の場で議論してよい問題は、[GitHub Issues](https://github.com/CodedagAI/codedag-home/issues) に投稿することもできます。
